# 06. 결과확인

작업물이 맞게 됐는지 **무엇을, 어떻게, 어떤 기준으로** 확인하는지 적는다. 화면별 결과는 `work/{id}-결과확인.md`에 적고, 01에는 상태만 적는다.

## 결과 표기

- `통과`: 실제로 실행해서 기준을 만족했다. 증거(명령, 행 수, 비교 대상)를 같이 적는다.
- `실패`: 기준을 만족하지 못했다. 고칠 때까지 ID는 `완료`가 될 수 없다.
- `해당없음`: 그 화면에 없는 기능이다(예: 삭제 버튼이 없음).
- `대기(일괄)`: 항목 7·7-1의 브라우저 시험을 도메인 단위 일괄 실행으로 미룬 상태(아래 "화면시험 지연"). 일괄 실행에서 통과하면 `통과`로 바꾼다. 도메인이 끝났는데 `대기(일괄)`가 남으면 `완료`로 보지 않는다.
- `미확인`: 확인하지 못했다. 이유를 적는다(03 원칙 11). 미확인이 남은 채로 `완료`하려면 사용자의 동의를 받는다.

## 화면시험 지연 (2026-10-19 사용자 결정)

화면마다 `tools/screens/{id}.js`(100~270줄)를 쓰고 고치는 비용이 커서, **ID 변환 중에는 브라우저 스크립트를 쓰지 않는다.**
- 변환 시 확인: 항목 1~6, 10, 11, 12. 항목 7·7-1은 `대기(일괄)`로 적고, `work/{첫글자}/{id}-화면시험.json` 명세(10~20줄: 메뉴 경로, API 접두사, 열 때 기대, 시험 행 키·셀·필수 안내·수정 칸, 특이 동작 메모)만 남긴다. 명세 내용은 `yunhee analysis ui/grid`와 작업방법에서 옮겨 적는다.
- 도메인 하나를 끝낸 뒤 `gen.js --all-pending`으로 그 도메인의 `대기(일괄)` ID를 한꺼번에 시험한다. 통과하면 각 `{id}-결과확인.md` 7·7-1을 `통과`로 바꾸고, 실패는 해당 ID 재작업.
- 일괄 시험은 admin 회사 계정만 쓴다(사용자 계정·중복 로그인 금지, 시작 전 사용자에게 알린다). 위험한 쓰기(여러 회사 행 채우기, 파일 삭제 등)는 명세에서 시험하지 않고 DB 테스트로 확인한다.
- 이전에 스크립트가 API·compare가 못 잡은 결함을 잡은 전례(C05, A08, C01-6 후속)가 있어 생략이 아니라 **지연**이다.
- 특이 동작(드래그, 모의 응답, 일반 사용자 모드 등)은 명세의 `custom` 훅 파일에 짧게 쓴다. 기존 A01~E30 스크립트는 그대로 두며 단건 재현에 쓴다.

- 실제로 실행하면 여러 테이블에 데이터가 남는 기능(회사 등록 등)은 화면에서 실행하지 않는다. SQL은 DB 시험(`@MybatisTest`, 롤백)으로, 화면은 서버가 거절하는 입력(중복 등)으로 끝까지 보낸다(`tools/screens/A15.js`).
- 고객사 메뉴(admin 회사에 없는 메뉴)는 admin 테넌트 로그인 화면에서 회사(예: kfstest)를 골라 그 회사 관리자로 확인한다.

- 같은 계정으로 로그인하므로 그 계정의 다른 세션(예: 사용자가 열어 둔 화면)은 중복 로그인 차단으로 끊길 수 있다.
- 확인 항목을 더하거나 바꿔야 하면 이 표를 고치고, 고친 사실을 그 ID 작업기록에 남긴다.
