바깥 `selectViolate`는 안쪽 `<sql id="selectViolate">`(L1406-1899, UNION ALL 14갈래 점검)와 `<sql id="selectEmp">`(L1184-1287, 사원별 기준값 CTE)를 포함한다. **`yunhee port-sql`·`analysis sql`은 안쪽 `include`를 자기 자신으로 잘못 풀어 `include selectViolate 없음`으로 나온다**(yunhee 수정사항 제안) → 원본 Read로 두 조각의 줄 범위를 확인한 뒤 `scratchpad/port_violate.py`로 그 범위를 그대로 옮기고 아래만 치환했다(손으로 560줄을 옮기면 틀리기 쉬워서).
1. `#{stdDate}` → `CAST(#{stdDate} AS date)` — 원본은 `java.util.Date`를 바인딩, 여기는 문자열.
2. **asseterpdb의 `flt10_tr`에는 협의승인 열 `flt10_add_confirmer_id`·`flt10_add_confirm_reason`이 없어** 원본이 돌지 않는다(I08에서 확인) → `<sql id="addConfirmerId">CAST(NULL AS bigint)</sql>`·`addConfirmReason`(`CAST(NULL AS text)`) 조각으로 바꿔 운영 DB에서는 이 두 줄만 원래 열로 되돌리면 된다. 효과: '사전신고 위반(미협의승인)' 갈래·`협조승인` 문구가 이 DB에서 나오지 않는다.
3. 조각 이름 `selectEmp` → `violateEmp`, `selectViolate` → `violateBody`(이 매퍼의 다른 조각과 안 겹치게).
4. `violateEmp`의 `noAccountSkipYnCheck != null` 가지(계좌 없는 사원 제외)를 뺐다 — 이 화면은 값을 안 줘 꺼져 있고, MyBatis는 `@Param`에 없는 이름을 `BindingException`으로 본다(첫 배포 때 500으로 확인).
5. 바깥 SELECT는 그리드 열만 DTO 열로 명시, 날짜 TO_CHAR. 끝에 `ORDER BY flt10_tr_id`(안쪽 `ROW_NUMBER()`와 같은 순서) — 원본은 바깥 정렬이 없지만 `ROW_NUMBER` 순서로 나와서 결과가 같다.

**AS-IS 대조 방법**: `mapper-run --compare flt10_tr.selectViolate`는 위 이유(include 오류 + DB 열 없음)로 못 돌린다. 대신 같은 SQL을 `mapper-run`으로 돌려 확인: 회사 28000, 기준일 2025-12-22 → 전체 70행, 사원 29049 → 16행. API(`yunhee api -c kfstest`)도 70·16행으로 같다.
