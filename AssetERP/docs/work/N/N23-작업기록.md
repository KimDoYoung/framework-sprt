## 결정 (사용자 확인 필요)
- **서버가 승인 대상 행을 다시 읽고 로그인 사용자의 행만 허용한다.** AS-IS는 화면이 보낸 모델(`firstApprEmpYn`·`finalApprEmpYn`·`apprStatusCode`·`checkStatusCode`·`companyId`…)을 서버가 그대로 믿었다. TOBE는 승인 행 ID(와 점검항목/조치내역 승인 행 ID)만 받고 같은 SQL(`selectByApprEmpId` 등)로 다시 읽는다. 화면 목록은 이미 로그인 사용자의 행만 보여 주므로 정상 흐름의 값은 같다. N22 "보안 제안"을 이 화면에서는 새로 만드는 코드라서 그대로 두지 않았다(AS-IS 동작이 바뀌는 것은 직접 조작한 요청뿐).
- **제출(`submit`)도 서버에서 "제출 가능" 검사를 한다.** AS-IS는 화면이 먼저 `checkTdmSubmitPossibleYn`을 부르고 서버 `updateSubmit`은 그 검사를 주석 처리했다. 화면 흐름은 같다(검사 → 확인 → 처리).
- **`f_get_tdmSubmitPossibleYn` 결과를 글자로 받는다.** 이 DB의 함수는 `boolean`을 돌려주는데 AS-IS 소스(`Tdm59_ChckApprCmnt.checkTdmSubmitPossibleYn`)는 'Y' 또는 불가 사유 문구를 기대한다(`!"Y".equals(msg)` → `result.fail(-1, msg)`). 이 DB에서 AS-IS 코드를 그대로 돌리면 항상 "t"가 문구로 나올 것이다. 운영 DB는 함수 버전이 다른 듯하다. `CAST(… AS text)`로 받아 'Y'·'t'·'true'는 통과, 'f'·'false'는 AS-IS 화면 코드 주석에 남은 옛 문구, 그 밖의 글자는 사유로 쓴다. DB는 못 바꾸므로(03 원칙 1) 이렇게 하고 사용자 확인을 부탁한다.
- **미흡/개선 내역 승인에서 "발생" 상태 행은 점검항목 승인 창(`Tdm52_Edit_ChckManlCmnt`)을 연다**(AS-IS 그대로). 그 점검항목은 `selectByChckApprCmntId`에 `chckManlId`를 줘서 한 건만 읽는다.
- `Tdm59_Edit_Cmnt`/`Tdm59_Edit_ReportCmnt`가 처리마다 부르는 `callBack.execute`는 목록 전체 재조회(`retrieve()`)를 한다(AS-IS 그대로). 창은 상태가 대기(10)로 남으면 열린 채로 폼만 갱신한다. 서버 응답은 처리 뒤 다시 읽은 승인 행이라 AS-IS가 돌려주던 모델(`apprStatusName`이 "승인"/"반려"/"대기")과 `apprStatusName`이 다르다("등록"/"미등록") — 창은 `apprStatusCode`만 쓴다.
- 의견 글자수 검사(`checkCmntLimit`)는 AS-IS가 주석 처리한 자리(SELF·SUB 승인 `A`, 점검항목 `Tdm60`)를 그대로 비워 두고, 반려(`R`)의 종합의견과 조치내역 승인·반려(`Tdm61`)에서만 한다.

## 메모
- **매퍼 변환 스크립트의 함정**: `:이름` → `#{이름}` 치환이 시각 서식 `'HH24:MI:SS'`의 `:MI`·`:SS`까지 바꿨다. `sql-check`(EXPLAIN)는 이것을 못 잡았고(주석 안이 아닌 문자열 리터럴이라 `#{MI}`가 바인딩 인자가 된 채 EXPLAIN은 통과) DB 테스트에서 `Parameter 'MI' not found`로 드러났다. 큰 SQL을 스크립트로 옮길 때는 시각 서식(`HH24:MI:SS`)을 따로 지켜야 한다. **yunhee 제안**: `sql-check --tobe`가 매퍼의 `#{…}` 이름이 `@Param` 이름과 다를 때(여기서는 `MI`·`SS`) 경고하면 좋겠다.
- **`mapper-run`은 `-p` 값을 글자로 보낸다.** `undoneYn=false`가 MyBatis `<if test="undoneYn">`에서 참으로 읽혔다(글자 'false'는 null이 아니라서). **yunhee 제안**: `api`의 `s:`/`n:`처럼 `b:false`(불리언 강제)를 `mapper-run`에도.
- **같은 이름의 DTO 덮어쓰기 사고**: `CheckApprRes.java`는 N21에 이미 있는 파일이었는데 새 DTO를 일괄 생성하다 덮어썼다. 시작 때 깨끗했던 파일이라 `git checkout`으로 복원하고 새 DTO는 `CheckApprListRes`로 이름을 바꿨다. 08 교훈에 적는다(새 이름이 겹치는지 먼저 `ls`로).
- yunhee `analysis screen`/`ui`는 이번에도 `getButtonBar().add(…)` 단추를 "도달 불가 (… 컬럼·툴바 미연결)"로 표시한다(`Tdm59_Edit_Cmnt`·`ReportCmnt`·`Tdm52_Edit_ChckManlCmnt`·`Tdm54_Lookup_ChckInsuffCmnt`의 등록·반려·취소·임시저장·닫기). 0.5.3·0.5.4에서도 그대로 — 실제로는 모두 연결된 단추. **yunhee 제안**: `ClassName.getButtonBar().add(button)` 패턴을 "창 단추줄"로 인식.
- 서버 로그에 `AuditLogService - 감사 로그 DB 기록 실패 (파일에는 기록됨) - event: WS_CONNECT`가 첫 배포 뒤 한 번 보였다(N22 때와 같은 것, 두 번째 배포 뒤에는 0줄). 이 ID와 관계 없다.

## 제안 (승인 대기)
- (부품) `GridBuilder.addLongCnt`/`addLongCntNull`(굵은 "N건", 헤더·값 색 지정) 렌더러를 `gb.longCnt(field, w, header, {headerColor, valueColor, nullBlank})`로 공통화 — 같은 코드가 `Tdm51_Tab_CheckOrg`·`Tdm52_Tab_CheckManl`·`Tdm59_Tab_CheckAppr`에 세 번 있다(03 원칙 15의 "세 번째" 기준). 승인하면 세 화면을 함께 고친다.
- (UX) 승인 의견 창들은 처리마다 위 목록 전체를 다시 조회하고 마지막 행을 다시 선택한다(AS-IS 그대로). 의견 하나를 등록할 때마다 사용자가 보던 행이 바뀐다 — 처리한 행을 유지하면 낫겠다.
- (정합) `Tdm59_ChckApprCmnt.updateApprCmnt`의 승인(`A`)은 점검항목·조치내역의 미승인 건수를 `chckApprCmntId`로 세지만 SELF 행은 자기 부서 점검항목이 없어 SUB 행들의 점검항목을 `tdm62_chck_cmnt_relate_org`로 거쳐 센다. 이 연결 테이블이 어긋나면 승인이 막히거나 통과할 수 있다 — 연결 테이블 생성(`createTdm59`)을 확인하는 시험이 필요하다(N21 범위).
