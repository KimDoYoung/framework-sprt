## API (새 9개, `bbs/notice-admin`)
`GET`(selectByPublicYnPaging·Total) · `GET next-id` · `PUT`(기록 insert + modelUpdate + 대상 고객사 insert) · `DELETE /{id}` · `GET/DELETE /{id}/target-companies` · `DELETE …/all` · `GET /{id}/histories` · `POST send-message`(sendNoticeMessage).

## SQL 이식
`selectBbsByPublicYn`(+Paging·Total, companyId 0, typeCode NoticeType002) / `bbs04_target_company` selectByNoticeId·insert·deleteAll / `bbs09_notice_history` selectByNoticeId·insert / `getNoticeNo` / 저장은 Z02와 같이 UpdateDataModel을 INSERT·UPDATE로 푼 것. 새 공지는 댓글허용 false. 기록 insert는 AS-IS 규칙 그대로(상태 또는 본문이 **창을 열 때 값**과 다르면 한 줄, 상태만 바뀌었으면 변경 전 본문 없음).

## 공통 절차와 다른 점 (원본과 다른 점)
- 문자 수신 번호는 클라이언트가 보내지 않고 서버가 사원 ID로 `emp01`에서 읽는다(번호 위조 방지). 번호 없는 사원은 건너뛴다(AS-IS는 빈 번호로 API 호출). 실제 발송은 `SmsSender`(기본 구현은 보내지 않음, 사용자 지시 2026-10-15).
- 새 공지는 저장할 때 목록에 넣고, 저장 뒤에도 창은 그대로 둔다(AS-IS 그대로 — "저장이 완료되었습니다."만 보임; 목록 줄은 반영).
- 관리자용 첨부 창 `Bbs02_Lookup_File.open`은 `Bbs15_Lookup_File` 재사용(Z02와 같음).
