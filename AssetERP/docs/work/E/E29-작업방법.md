## SQL 이식
- `ast05_tr_code.selectByCompanyId`·`selectById`: `select *`를 DTO 열로 풀었다. 그리드에 없는 계산 열(`act11_tr_map` 장부구분·자산분류명·문서분류명)과 그 JOIN은 뺐다(원본 화면이 쓰지 않음). 수령/지급·거래발생구분 이름은 `f_cdnm` 그대로
- `ast15_tr_code_window.selectByAll`·`selectByClassName`·`getTrCode`·`selectById`: DTO 열로 풀었고, 열이 다른 SELECT는 `NULL AS …`로 맞췄다(record 생성자 매핑)
- `sys06_menu.selectByText`: 두 SELECT의 UNION(권한 역할 / 회사 기본 역할)을 그대로, `menuNameYn`에 따라 화면명만/화면설명 포함 검색. `a.*`는 DTO 열로 풀고 `ORDER BY`를 쓰려고 `sys06_parent_id`·`sys06_seq`를 별칭으로 남겼다(sql-check 경고 "미사용 별칭"은 이 때문)
- `selectByTextManager`: 원본이 `userId`를 안 넘겨 `sys51_person_id = NULL`이 된다 → 서비스가 `null`로 부른다
- `sys40_bookmark.insertMenuId`: `nextval('bookmarkseq')` 그대로

## 공통 절차와 다른 점
- 회사 범위: 거래코드 저장·삭제는 로그인 회사만(SQL에 회사 조건), 기초데이터생성은 **관리자 회사만** 서버가 검사(원본은 막지 않았다), 고객사마다 서비스를 따로 부르던 것을 한 트랜잭션으로. 화면별 거래유형은 `user.companyOf(요청 회사)` — 관리자 회사만 다른 운용사를 고를 수 있다
- 필수 검사(거래코드·거래명·수령/지급)·중복 코드 검사는 서버도 같은 문구로 한다(원본은 화면 + 서버 `update`)
- 행 끌기: 같은 그리드 안의 순서 바꾸기(GridDropTarget의 INSERT 피드백)는 두지 않았다 — 조회가 코드순이고 저장이 순서를 쓰지 않아 결과가 같다
- 화면별 거래유형의 [삭제]는 화면 행만 지운다(거래코드 지정 행은 남는다 — 원본 동작). 지운 뒤 오른쪽 페이지는 다시 읽지 않는다(원본 그대로)
- 초기화(UX-02)는 넣지 않는다: 툴바가 두 줄(72px)로 넘어간다
