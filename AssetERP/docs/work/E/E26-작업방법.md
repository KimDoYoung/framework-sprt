## SQL 이식
- `selectByCompanyId`·`selectByEvalListStdId`(41·42)·`selectByMaxCompanyId(Admin)`(41·42): `SELECT *`를 DTO 열로 풀었다. 정렬 `ORDER BY emp40_start_date DESC`·`emp41_seq`·`emp42_grade_score DESC` 그대로. `selectByMax…`는 원본에 ORDER BY 없음.
- 저장(UpdateDataModel): 새 행(ID 0 이하·없음)은 `f_create_seq()`로 ID를 받아 INSERT, 아니면 UPDATE, 삭제는 ID로 DELETE. `emp41`·`emp42`에는 회사 열이 없어 **`evalListStdId`가 로그인 회사 것인지 먼저 검사**하고 WHERE에 `…_eval_list_std_id = #{evalListStdId}`를 더했다(원본 SQL엔 없음, E25의 회사 조건과 같은 이유).
- `getEventChk`는 `SELECT *` 후 건수만 쓰므로 `COUNT(*)`로 옮겼다(결과 같음).

## 공통 절차와 다른 점
- grid02 저장은 원본처럼 **모든 행**(빈 새 행 포함)과 삭제대기를 한 번에 보낸다. 가중치 합계 검사도 **모든 행**으로 한다. 값이 비어 있으면 원본은 NPE(조용히 실패)라서 TOBE는 0으로 센다.
- 삭제대기가 있는 저장(n)은 E21처럼 `변경 + 삭제대기` 건수로 센다(UX-03). 변경도 삭제대기도 0건이면 저장이 비활성이라 원본의 "합계 100 검사"를 변경 없이 부를 수 없다.
- 서버 상태 -1/-2는 `BusinessException(INVALID_INPUT/DUPLICATE_DATA, 원본 메시지)`로 옮겼다. 화면은 `errorMessage()`로 같은 문구를 보인다.
- 합계 행(`getSumGrid("합계", 3, 4, 5)`)은 `sumRow`로: 라벨 열 `content`, 합 `weightMember`·`weightLeader`.
