## 공통 절차와 다른 점
- **서버가 단추 권한을 다시 계산한다**: AS-IS는 클라이언트가 켠 단추의 요청을 서버가 그대로 믿고 `stepEmpId`·`apprEmpId`까지 클라이언트 값을 썼다. TOBE는 로그인 사원으로 서버에서 `myTurnCheck`/`myCancelApprovalCheck`/`retrieveApproval` 판정을 다시 해 해당 없는 처리는 막고, 결재자 ID도 서버가 정한다(대결이면 `stepEmpId` = 원결재자).
- **결재선 순서**: `retrieveApproval`의 `store.get(0)` 판정은 상신자가 첫 줄이라는 의도다. `buildApprStepGrid`의 `StoreSortInfo(stepStatusCode)`가 실제로 먹는지는 AS-IS 화면에서 확인하지 못해 단추 판정과 V01 결재선 표시를 서버가 주는 seq 순서로 했다. 먹는다면 대기 단계가 위로 오고 [상신취소]가 사라진다 — 7(화면시험)에서 원본과 비교.
- **알림 미발송**: `confirmUpdate`·`clearApprStepId`는 다음 결재자·상신자·참조자에게 앱알림(SendTalkAPI)·메일(SendMailMaster)·SMS(`sendSMSToNextApprStep`)를 보낸다(`emp92_sms_notice` 수신설정 확인 포함). TOBE에는 이 발송 부품이 없고(`SmsSender` 인터페이스·`MailServerConfig`만) 시험 중 실제 발송을 막으려고 **만들지 않았다**. 승인·반려·승인취소 때 알림이 가지 않는다 → 작업기록 제안.
- **PDF**: 결재가 끝나고 인감(`stampId`)과 인감대장번호가 있으면 AS-IS는 `utils.pdf.PDFCreate.createPDF7`로 PDF를 만든다. 서버는 `makePdf=true`를 돌려주고 화면은 "V04에서 연결"을 알린다(PDF는 만들지 않는다).
- **트랜잭션**: AS-IS는 `confirmUpdate` 중간에 `commit`했다. TOBE는 한 요청을 한 트랜잭션으로.
- 상신취소 결과: 링크 문서 폐기의 `apr99_appr_del.apr99_del_emp_id`는 AS-IS 요청에 사원이 없어 비는데(`:empId` 값 없음) TOBE는 로그인 사원을 남긴다.
- 반려사유는 비어 있거나 빈 글이면 "반려사유 미입력"(AS-IS는 `null`만 처리).
