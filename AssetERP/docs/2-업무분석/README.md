# 업무분석

## 개요

- 업무분석이란 ASIS의 소스를 분석하여 각 도메인별 업무의 흐름을 분석한 후 그것이 TOBE에 적절히 적용되었는지를 판단한다.
- 업무분석 결과 TOBE의 구현이 적절하지 않은 경우 이를 판별하여 사용자에게 문서로서 보고를 한다.
- 보고는 명확하게 시나리오를 갖고 보고되어야 한다.
- 보고는 UI의 흐름과 DB의 변경을 함께 보고되어야 한다.

- 이벤트를 찾고, 시나리오를 만들고, 따라 하고, 자동 시험을 돌리다가 **AS-IS든 TOBE든** 보안 문제나 버그로 의심되는 것을 보면 **바로** [`보안_및_버그_의심.md`](보안_및_버그_의심.md)에 한 줄 적는다(2026-11-10 사용자 결정). 확실하지 않아도 `의심`으로 적는다. 미루지 않는다.

## 가상의 회사를 생성하여 시나리오를 만든다.

- kalpa,kova,igo 3개의 id로 가상의 회사를 만든다.
- 3회사의 admin 계정은 admin/1111이다(직원도 모두 1111).
- 3회사는 사장, 부장, 과장, 사원 4계층으로 한다(아래 "직원·조직·메뉴 규칙").

### 직원·조직·메뉴 규칙 (2026-11-09 결정, kova·igo에 적용)

가상 회사는 **직급 4개**(사장·부장·과장·사원)만 둔다. 사번에 직함을 넣는다.

| 사번 | 직함(직위/직책) | 이름 | 소속 |
|:---|:---|:---|:---|
| 100 | 사장 / 대표이사 | 김사장 | 회사 |
| 201 | 부장 / 본부장 | 박부장 | 경영지원본부 |
| 202 | 부장 / 본부장 | 정부장 | 운용본부 |
| 301 | 과장 / 팀장 | 김과장 | 경영지원본부 |
| 302 | 과장 / 팀장 | 박과장 | 운용본부 |
| 401 | 사원 / 팀원 | 김사원 | 경영지원본부 |
| 402 | 사원 / 팀원 | 최사원 | 운용본부 |

- 사번 규칙: 직함 번호(`1xx` 사장 · `2xx` 부장 · `3xx` 과장 · `4xx` 사원) + 순번. 직원 7명, 조직은 회사 1 + 본부 2(경영지원본부 10100, 운용본부 10200).
- 메뉴 출발지: **가장 작은 회사 `prod_s1`**(SYS-BZ-0003 메뉴 복사). 상품 코드 `S1`. 관리자 `admin` 메뉴 59개, 직원은 사원 12개·사장·부장 15개·과장 30개(2026-11-09).
- 권한: 권한그룹 `임원`(경영관리 > 조직 및 사원관리 메뉴 5개)을 사장·부장에게, 과장에게는 `경영 관리자`를 준다. 사원은 기본권한(`일반 사용자`)만.
- 회사: `kalpa` (주)칼파테크 220-81-11111, `kova` (주)코바 220-81-22222, `igo` (주)아이고 220-81-33333. 한 번에 만들기: `tools/create-virtual-company.sh <회사ID> "<회사명>" <사업자번호>`(먼저 `tools/db_dump_backup.sh`, 다시 만들려면 `tools/delete-company-db-data.sh <회사ID> --all`).
- 세 회사(kalpa·kova·igo) 모두 이 규칙이다. kalpa는 처음에 출발지를 `kfstest`(관리자 메뉴 395개)로 만들었다가 2026-11-09 규칙을 정한 뒤 지우고 다시 만들었다.
- **kalpa만 예외 — EMP 업무 메뉴 29개 추가**(2026-11-10 사용자 결정). S1 상품에는 EMP 업무 화면(휴가·출장·급여공제·증명서·인사평가 등)이 없어서, KFS가 #1076 회사별 메뉴맵핑으로 메뉴 29개 + 상위 폴더 10개를 넣고(SYS-BZ-0003 방식) 회사 관리자가 #1070에서 권한그룹에 줬다(SYS-BZ-0005 방식). 그 뒤 메뉴 수: 관리자 88 · 사장·부장 27 · 과장 58 · 사원 21. 나눈 방식은 [EMP 흐름도](biz-event/EMP/EMP-업무흐름.md#가상-회사-kalpa의-메뉴-범위). kova·igo는 그대로다. ### 비밀번호 규칙 (2026-11-12 변경 — 모두 `1111`)

**모든 계정의 비밀번호는 `1111`이다**(시험 편의, 2026-11-12 사용자 결정). KFS 관리자 `admin/admin`, 각 회사 관리자 `admin`, 직원(사번 로그인) 모두 같다.

- 직원 비밀번호는 원래 규칙(`f_password_rule`: 8자리 이상·반복문자 2회 제한)상 `1111`을 화면·API로는 정할 수 없다. 그래서 `sys25_password`에 직접 넣는다(로컬 asseterpdb 쓰기 — 아래 "로컬 DB 쓰기").
- 2026-11-09~11에는 직원 비밀번호를 `Kalpa1234!`로 정해 SYS-BZ-0012(`POST /api/auth/password/change`)로 설정했다. 그 뒤 2026-11-11 01:45에 kalpa 직원 7명이 `1111`로 바뀌어 있었고(2026-11-12 확인), 이 규칙으로 정리했다. 옛 문서의 `Kalpa1234!`는 `1111`로 읽는다.
- `yunhee api`로 직원 로그인: `YUNHEE_TEST_ACCOUNTS="401:1111" yunhee api … -u 401 -c kalpa`(사번이 다른 회사와 겹치면 사원 ID로 `-u`).

### 로컬 DB 쓰기 (2026-11-12 사용자 결정)

- localhost asseterpdb는 시험·분석을 위해 얼마든지 CRUD 해도 된다. 다만 에이전트는 셸에서 `psql`로 직접 쓸 수 없으므로(훅이 막음) **필요하면 SQL을 사용자에게 알리고** 사용자가 `! psql …`로 실행한다. 먼저 `tools/db_dump_backup.sh`.
- 쓰기 SQL 미리 시험은 `yunhee sql -f x.sql --rollback`.
