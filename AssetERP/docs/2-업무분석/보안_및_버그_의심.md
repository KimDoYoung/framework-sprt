# 보안 및 버그 의심 — 업무분석 중 발견 기록

업무분석(이벤트 찾기·시나리오 만들기·따라 하기·자동 시험)을 하다가 **AS-IS든 TOBE든** 보안 문제나 버그로 의심되는 것을 보면 **그 자리에서 바로** 여기에 한 줄 적는다(2026-11-10 사용자 요청). 나중에 적으려고 미루지 않는다. 확실하지 않아도 "의심"으로 적고, 확인하면 상태를 바꾼다.

## 원본-이상한점.md 와의 관계

- `../원본-이상한점.md`는 **변환** 중 원본을 그대로 옮기면서 만난 이상한 점(사용자 판단 대기)이다. 그 목록도 하나씩 검증해야 한다.
- 이 파일은 **업무분석** 중 발견한 보안·버그 의심이다. TOBE 쪽 문제(변환 실수, 서버 검사 누락 등)도 여기에 적는다.
- 같은 문제가 이미 `원본-이상한점.md`에 있으면 새로 설명하지 말고 `관련` 칸에 `이상한점 #번호`로 잇는다. 그 항목을 업무분석에서 재현·확인했으면 결과를 여기 적는다.

## 적는 법

| 칸 | 쓰는 것 |
|:---|:---|
| # | 일련번호. 지운 번호는 다시 쓰지 않는다 |
| 발견 | 이벤트 ID(`SYS-BZ-0012` 등)와 날짜 |
| 구분 | `보안`(권한·인증·다른 회사 데이터·입력 신뢰·정보 노출) / `버그`(잘못된 결과·오류·데이터 깨짐) |
| 쪽 | `AS-IS` / `TOBE` / `둘 다` |
| 화면 | 화면번호 · 메뉴 경로(번호 없으면 여는 화면 번호와 방법, 루트 CLAUDE.md "화면번호 중심") |
| 위치 | 원본 `클래스.메서드 L줄` / TOBE `파일:줄` / SQL ID |
| 내용 | 무엇이 왜 문제인가 한두 문장 |
| 재현 | 누가(회사·사번) 무엇을 하면 무엇이 일어나는가. 이벤트 상세의 따라 하기 단계나 `yunhee api`·`sql` 명령 |
| 심각도 | `상`(다른 회사·남의 데이터 접근, 권한 우회, 데이터 손실) / `중`(잘못된 결과·오류) / `하`(표시·불편) |
| 상태 | `의심`(확인 전) → `확인`(재현됨) / `아님`(오해였음, 이유 적음) → `조치`(고친 커밋·날짜) / `보류`(사용자 판단 대기) |
| 관련 | `이상한점 #번호`, 관련 이벤트·문서 링크 |

- 재현할 때 DB 쓰기는 먼저 `tools/db_dump_backup.sh`. 보안 재현으로 다른 회사 계정 로그인을 반복하지 않는다(계정 잠금 — `AssetERP/CLAUDE.md` 실수 목록).
- 고치는 것은 이 파일에 적은 뒤 사용자 결정으로 한다(AS-IS 동작을 바꾸는 TOBE 수정은 승인 필요).
