# 05. 작업방법

04의 각 작업을 **어떻게** 하는지 적는다. 모든 ID에 공통인 것만 여기에 두고, 화면마다 다른 것은 `work/{id}-작업방법.md`에 둔다.
색인 만들기(B01·B02)는 저장소 루트(`framework-sprt/`)에서, 그 밖의 명령(`yunhee analysis`·`compare`·`api`·`run` 등)은 **`AssetERP/`에서** 실행한다. `yunhee analysis`는 루트에서 돌리면 AssetERP 색인을 못 찾는다(`screen`·`ui` 오류, `method`는 E-id가 빠짐).
도구 사용의 원칙은 `../../CLAUDE.md`의 yunhee 절, **어떤 경우에 어떤 yunhee 명령을 쓰는지는 §7 "A 작업 단계별 명령" 표**가 기준이다. 아래 절차의 각 단계도 그 표의 명령으로 한다.

## 0. ID 하나를 시작하고 끝내는 법 (B·A 공통)

> **`docs/work/` 폴더 규칙**: 파일명 첫 글자로 하위 폴더에 둔다. `A01-작업기록.md` → `docs/work/A/`, `E10-결과확인.md` → `docs/work/E/`, `yunhee-*` → `docs/work/yunhee/`. 새 ID 파일은 해당 글자 폴더에(없으면 `mkdir`로 새 폴더 — 예: F01 → `docs/work/F/`) 만들고, `docs/work/` 바로 아래에는 파일을 두지 않는다. `drift --note-file`·`baseline.json`의 note 경로도 `docs/work/{첫 글자}/{id}-작업기록.md`로 쓴다.

1. 01에서 상태가 `대기`인 첫 ID를 고른다(04 순서). 01의 상태를 바꾼다.
2. `work/{id}-작업기록.md`를 만든다(§4 템플릿). A는 `work/{id}-작업방법.md`(§3)와 `work/{id}-결과확인.md`(06 템플릿)도 만든다. 브라우저 시험은 미루고 `work/{id}-화면시험.json`(명세, 06 "화면시험 지연")만 남긴다.
3. 아래 절차대로 작업하면서, 한 일·막힌 점·결정을 작업기록에 바로 적는다.
4. 끝나면 비용을 정리한다(작업기록의 "비용" 절. 빌드·테스트 횟수와 실패 수는 `yunhee runs`에서 옮긴다). 01을 `완료`로 바꾼다. 그리고 **AS-IS 기준을 남긴다**: `yunhee drift --record <화면 클래스> --id {id} --note-file docs/work/{ID 첫 글자}/{id}-작업기록.md` (색인이 최신이어야 한다 — §7 "원본 변경 점검").
5. 공통 절차를 바꿔야 했다면 이 문서나 06을 고치고, 공통 프론트 부품을 만들거나 바꿨다면 `11-프론트부품.md`와 §5 등록표를 고치고, 그 사실을 작업기록에 남긴다(03 원칙 10·15).
6. 다음 회차에 도움이 될 교훈이 있으면 `08-회차인계.md`의 "교훈" 표에 한 줄 적는다.

**묶음 세션(03 원칙 8)**: 세션 시작(03·01·05 읽기, `yunhee --version`)은 1번만. 1~6은 ID마다 반복한다 — 작업방법·작업기록·결과확인은 ID별로 따로 만들고(합치지 않음), 빌드·deploy·`drift --record`도 ID마다 한다. 비용 절에 "묶음 세션, 시작 비용 공유"와 ID별 소요시간을 적는다. 08 교훈은 묶음 끝에 한 번. 병렬 세션은 쓰지 않는다(01·공통 부품표·Tomcat·DB 공유로 충돌).

### B01 명령

```bash
# 메뉴 TSV (asseterpdb sys06_menu, 경로·화면번호 포함)
psql -h localhost -U kdy987 -d asseterpdb -AtF $'\t' -c "
WITH RECURSIVE t AS (
  SELECT sys06_menu_id id, sys06_menu_nm::text path, sys06_seq::text sort FROM sys06_menu WHERE sys06_parent_id = 0
  UNION ALL
  SELECT m.sys06_menu_id, t.path || ' > ' || m.sys06_menu_nm, t.sort || '.' || coalesce(m.sys06_seq,'')
  FROM sys06_menu m JOIN t ON m.sys06_parent_id = t.id)
SELECT coalesce(m.sys06_menu_no,''), t.path, m.sys06_class_nm, coalesce(m.sys06_use_yn,'')
FROM t JOIN sys06_menu m ON m.sys06_menu_id = t.id
WHERE coalesce(m.sys06_class_nm,'') <> '' ORDER BY t.sort" > AssetERP/docs/as-is/menus.tsv

# DB 스키마가 바뀌었으면 먼저: yunhee dbml YUNHEE_DB -o .yunhee/asseterp-dbml.md
yunhee index-db .yunhee/asseterp-dbml.md -t AssetERP/docs/as-is/db
yunhee index-src -t AssetERP/docs/as-is/src   # 원본은 YUNHEE_ASIS_SRC_DIR(`yunhee config`, 2026-10-13부터 ~/work/IDMS-IC). menus.tsv·db는 -t의 상위 폴더에서 찾는다
```
- index-db를 다시 돌렸으면 index-src도 다시 돌린다(테이블 링크와 `⚠DB없음` 판정이 DB 색인을 쓴다).
- `-t`에는 색인 전용 폴더만 준다(실행할 때마다 그 아래 *.md를 지운다). 루트의 `docs/as-is/`는 OMS 색인이므로 쓰지 않는다.
- **`psql`이 암호를 물어 멈추면**(2026-10-19 E26: 색인이 없는 PC) 위 menus.tsv 대신 `yunhee sql --builtin menus -o tsv --no-header --out AssetERP/docs/as-is/menus.tsv`를 쓴다(접속정보를 yunhee가 가진다, 507행). 그 뒤 `yunhee run -t 600 "bash -c 'yunhee index-db … && yunhee index-src …'"`(약 2분).
- **`yunhee api`·`compare`가 로그인에서 404**면 `.env.yunhee`(0.5.0~, 옛 `.env.local`도 읽음)의 `YUNHEE_API_BASE_URL`(Tomcat 기본 주소)이 이 PC에 없는 것이다 — `--base http://localhost:8082/AssetERP`를 주고 경로는 `/api/v1/…`로 쓴다(`/v1/…`만 쓰면 `No static resource` 404).

## 3. `{id}-작업방법.md` 템플릿 (A)

```markdown
# {id} {클래스} — 작업방법

- 메뉴: {경로} #{화면번호}   색인: [../as-is/src/sys/screens/{클래스}.md]
- 원본: `client/vi/sys/{클래스}.java` ({줄}줄), 함께 쓰는 클래스: …

## 이벤트 → TOBE
| E-id | AS-IS (이벤트 → 메서드 L범위) | TOBE에서 할 일 | API |
|:---|:---|:---|:---|

## API
| 메서드 경로 | AS-IS 서비스 | 서버 L | SQL ID | 비고 |
|:---|:---|:---|:---|:---|

## SQL 이식
| SQL ID | 테이블 | 그대로 / 수정(사유) |
|:---|:---|:---|

## 화면 구성
- 레이아웃, 그리드(GridType·컬럼), 버튼(type), 팝업

## 공통 절차와 다른 점
- (없으면 "없음")
```

**TOBE 매퍼의 AS-IS 출처 주석 (2026-10-15, yunhee 0.3.3~)** — SQL을 옮기거나 다시 맞추면 statement 위에 `<!-- AS-IS {sqlId} L{줄} (IDMS-IC) … -->`를 단다. `(IDMS-IC)`는 새 원본(`~/work/IDMS-IC`) 기준이라는 표시다. 파일 전체가 새 원본 기준이면 머리 주석을 `AS-IS(IDMS-IC) server/…/{매퍼}.xml …`로 쓴다. 표시가 없는 statement는 옛 원본(`~/oms-data/src/Asset-ERP`) 기준으로 보고, `yunhee sql-check --old`가 원본이 바뀌었으면 알린다(§7 "백엔드" 행). 출처 주석이 없으면 `⚠ 출처 없음`으로 모이므로 AS-IS에서 옮긴 statement에는 꼭 단다.

### 세션 시작
- `yunhee --version` → 이 절의 기준 버전보다 높으면 `yunhee changelog --since 0.5.4`로 **바뀐 것만** 읽고, 쓸 만한 기능이 생겼으면 이 절을 고친다(작업기록에 남김).
- yunhee가 바뀌어 색인 결과가 달라질 수 있으면 색인을 다시 만든다(§1 B01 명령).
- **원본 변경 점검 (0.3.8~)**: AS-IS 원본(`~/work/IDMS-IC`)은 매일 바뀐다. 사무실·집 PC 모두 `git pull`한 직후에, 그리고 이미 끝낸 ID를 다시 볼 때 아래 순서로 본다.
  1. `git -C ~/work/IDMS-IC pull` → `yunhee index-src …`(§1 B01)로 색인을 다시 만든다. 끝 줄 `지난 색인 대비 변경 화면 N개`와 `소스 <커밋> (<브랜치>) clean`을 본다. `dirty`면 baseline을 기록하지 않는다. 색인의 기준 커밋과 소스 HEAD가 다르면 `yunhee drift`가 경고한다.
  2. `yunhee drift --all --done-only --base baseline` — 완료 화면 중 **내가 변환한 뒤 원본이 바뀐 것**만 한 줄씩(파일 수·+/-줄·마지막 커밋). 공유 서비스·매퍼가 바뀌면 `(공유 N)`으로 영향 화면에 표시된다. 변경 0개면 끝.
  3. 바뀐 화면은 `yunhee drift <화면> -o diff`로 diff만 보고, 필요한 곳만 TOBE에 반영한다(전체 재변환 안 함). 반영하면 `yunhee drift --record <화면> --id {id} --note-file docs/work/{ID 첫 글자}/{id}-작업기록.md`로 기준을 갱신하고 작업기록에 한 줄 남긴다.
  - 기준 파일은 `docs/baseline.json`(`.yunhee.toml`의 `[drift] baseline`, git으로 공유)이다. 화면별 한 줄 `AS-IS 기준:`은 `docs/work/{ID 첫 글자}/{id}-작업기록.md` 머리에 있다. `.yunhee/baseline.json`은 쓰지 않는다.
  - `--base index`는 "지난 색인 이후", `--base baseline`은 "내가 변환한 이후", `--base <커밋>`은 임의 시점 대비다. 새 ID는 `확인`(구현·배포 끝) 단계에서 기록해도 된다 — `--done-only`는 baseline이 있는 화면을 본다.

### `yunhee log` — 서버 로그 (0.2.5~)
- 기본 대상은 Tomcat 배포본(docker `t3600-tomcat`, `~/tmp/asseterp-data/logs`, 접두어 `AssetERP-backend`). 출력 시각은 **UTC**(trace 요약에 KST 병기)지만 `--from`·`--to` 입력은 **KST**(헤더의 범위로 확인). `--tz`는 표시 시간대가 아니라 '로그 파일이 쓰인 시간대'라서 docker 로그에 `--tz KST`를 주면 결과가 비게 된다 — 쓰지 않는다. bootRun 로그는 `--source local --dir <폴더>`. 개인정보는 기본 마스킹(`--no-mask`).
- 모든 요청에 trace ID가 붙는다. 요약 한 건 = 요청·상태·시간·사용자(회사:ID) + SQL 목록(매퍼.ID (파라미터) → 행 수) + WARN/ERROR. 원문이 꼭 필요할 때만 `--raw`.
- 언제 쓰나:
  | 상황 | 명령 |
  |:---|:---|
  | `yunhee api`가 4xx/5xx·행 수 이상 | 처음부터 `api … --log`로 부른다. 행 수가 다르면 `log trace <id> --sql` → `yunhee sql`로 같은 SQL 실행 |
  | 저장 API가 무엇을 썼나(부수 효과 확인) | 같은 값 PUT 후 `--log` → INSERT/UPDATE 목록을 `port-save` 부수 효과 목록과 대조 |
  | `./deploy.sh` 직후 | `yunhee log errors --since-deploy` (기동 오류·매퍼 로딩 실패) |
  | 브라우저 스크립트(tools/screens) 실행 후 | `yunhee log tail --since 5m [--level WARN]`(스크립트가 부른 API·상태·SQL 수. `--since-run`은 0.2.7 결함), 실패 요청만 `log trace` |
  | **사용자가 화면 오류를 알림** | 재현하기 전에 `yunhee log req <METHOD> <경로 일부> -n 5 --trace`(또는 `log tail --since 10m`, `--from 15:10 --to 15:20`은 **KST**로 입력) → 사용자 요청의 파라미터·SQL·예외를 본다. 사용자 계정으로 로그인해 재현하지 않는다 |
  | 느린 API | `log tail`·`log req`의 ms 칸 → 해당 trace의 SQL |
- 0.2.7(2026-10-12): 수정사항022·023 반영(`--archived`가 `req`·`errors`·`tail`에도 동작, 지난 날 시각에 날짜 표기). 검증 57/57. 남은 것: `--since-run`의 기준 시각이 run **끝** 시각이다(`yunhee runs`의 Created At = 끝, run ID = 시작) → 스크립트를 `yunhee run`으로 돌린 뒤 `--since-run last`를 쓰면 실행 중 요청이 모두 빠진다. 고쳐질 때까지 `--since 5m`처럼 기간으로 본다.
- `log errors --explain`은 qwen 요약이라 참고만 한다. 판단은 trace의 원 메시지로 한다.

## 8. AS-IS 공통 그리드 클래스 동작 (2026-10-12, C01-6 후속)

AssetERP 화면의 그리드 CRUD는 거의 모두 아래 4개 공통 클래스(`client/service/`)와 서버 `UpdateDataModel`을 거친다. 화면 코드에 안 보이는 동작이 여기서 정해지므로 **TOBE `useGridCrud`는 이 표와 같게 동작해야 한다**(사용자 결정: 공통으로 원본과 같게).
화면을 분석할 때 `insertRow`·`update`·`deleteRow`가 이 클래스를 쓰면 아래 동작을 전제로 하고, 다르게 쓰는 화면(직접 `ServiceCall`, `update(store, 모델, …)` 단건 등)만 작업방법에 따로 적는다.

| 동작 | AS-IS 클래스 | 원본이 실제로 하는 일 | TOBE (`useGridCrud`) |
|:---|:---|:---|:---|
| 조회 | `GridRetrieveData.retrieve` | 서버 결과로 store를 `replaceAll` — 저장 안 한 변경·새 행은 **묻지 않고 버린다** | `retrieve`: 목록 교체 + 변경 표시 지움 |
| 행 추가 | `GridInsertRow.insertRow(grid, 모델[, 콜백])` | 서버 `getSeq`로 ID만 받아 선택 행 아래(없으면 끝)에 `store.add` + 선택. **DB에 쓰지 않고, 변경(modified)도 아니다**. 콜백에서 `getRecord(행).addChange(…)`로 넣은 값만 변경이 된다 | `addRow()`: 임시 음수 ID, 변경 아님. 원본이 콜백에서 `addChange`하면 `addRows(inits, true)`(Sys05 사원찾기), 일부 조건에서만 하면 그 조건으로(Emp03 조직) |

| 저장 | `GridUpdate.update(store, 서비스[, 콜백])` | `getModifiedRecords()`만 모아 보낸다. **0건이면 서버도 안 부르고 메시지도 없다**. 결과 행으로 store를 갱신(있으면 update, 없으면 add). 서버는 `UpdateDataModel`: ID가 DB에 있으면 UPDATE, 없으면 INSERT, 필수값 검사 없음(일부만 채운 행도 저장) | `saveRows`: 변경 행만, 0건이면 조용히 끝. 결과 행으로 제자리 교체 |

| 저장 전 검사 | `listStore.getModifiedRecords().size() > 0` 등 | 화면 코드가 직접 | `hasChanges()` |

- 그래서 "등록 → (입력 없이) 저장"은 원본에서 아무 일도 없다. 새 행은 다음 조회 때 사라진다.
- 원본이 클라이언트 모델을 서버로 넘기는 처리(예: 교육사항 일괄등록 `multiUpdate`)는 **저장 안 한 새 행이면 빈 값**이 넘어간다 → TOBE도 DB 행 ID가 아니라 화면 행 값을 보낸다.
