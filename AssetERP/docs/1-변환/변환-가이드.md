# 변환 가이드

GWT/GXT 화면을 Spring Boot + React로 옮길 때 지키는 것 전부. 세션 시작에 이 문서 하나를 통째로 읽는다(2026-11-05, 옛 03·05·06·12를 합침. 옛 문서는 `_보관/`).
**규칙을 바꾸는 것은 사용자만 한다.** 부딪히면 작업을 멈추고 묻는다. ID별 작업방법·작업기록·결과확인 파일은 만들지 않는다.

## 1. 원칙

**데이터**
- DB는 로컬 `asseterpdb` 하나. 테이블·컬럼·함수를 만들거나 바꾸지 않는다. 필요한 것이 DB에 없으면 그 ID는 `보류`하고 사유를 목록에 적는다.
- 확인은 데이터를 바꾸지 않는다. 저장 API 시험은 같은 값 PUT, 시험 행은 만든 세션 안에 지운다.

**원본이 정답** (AS-IS는 오래 다듬어진 상용 서비스)
- 원본을 통째로 읽지 않는다. 색인에서 파일·줄을 찾아 그 줄만 연다.
- 레이아웃, 버튼(개수·순서·문구), 이벤트 E0~En 전부, 그리드(종류·컬럼 순서/폭/제목), 메시지, SQL을 그대로 옮긴다. SQL이 DB에서 안 돌 때만 고치고, 그때 원래 SQL과 이유를 코드 주석에 남긴다.
- 개선은 하지 않고 제안만 한다(채팅으로 알린다). 승인된 개선: UX보강(`10-UX보강.md` 등록표에서 `부품완료`인 것만, 공통 부품으로만), 등록 행은 맨 아래, 헤더 정렬 없음, 저장·삭제 성공 메시지.
- 그리드 종류: `setChecked` 없으면 `SingleGrid`, 있으면 `MultiGrid`, 컬럼에 편집기가 있으면 `CellEditGrid`+`useGridCrud`. 행번호는 `setRowNumHidden(true)`가 아니면 보인다. 헤더 클릭 정렬은 만들지 않는다.

**TOBE 규칙**
- 패키지·레이어: `docs/TOBE-Framework.md` (`kr.co.kfs.asseterp`). OMS 코드는 복사하지 않는다.
- 화면 레이아웃: 바깥 `div`는 `height:'100%', padding:20, boxSizing:'border-box'`. 테두리·padding 있는 `div`가 `height:'100%'`면 `boxSizing:'border-box'`. 스크롤바는 그리드 안쪽 하나만(`99%`로 줄이지 않는다). 간격 8, 라벨·입력 오른쪽 정렬.
- 정렬은 `COLLATE "ko_KR.utf8"` 그대로(`ko-KR-x-icu`로 바꾸지 않는다). 그리드 셀은 세로 가운데(`BaseGrid` 기본).
- 조회창은 `LookupModal`(첫 입력칸 포커스, 행 클릭 선택 `<MultiGrid rowClick>`), 편집창(`*_Edit_*`)은 EditModal 규격(`11-프론트부품.md` §4a). 조회창 폭 = 열 폭 합계 + 약 190, 1120을 넘으면 스크롤 허용.
- 그리드 [등록]은 항상 맨 아래에 빈 행을 만들고 스크롤한다(`useGridCrud insertAt`).
- `_Tab_` 화면은 `yunhee page-style <원본.java>`로 SID를 확인하고 `docs/page-style/{SID}/` **견본을 뼈대로** 만든다. 끝에 `yunhee page-style --compare <원본.java> <TOBE.tsx>`가 `일치`, 규칙이 있는 SID는 `python3 -I tools/page-style-check.py <SID>`. 표에 없으면 사용자에게 알리고 새 SID로 먼저 등록한다. 머리 주석에 `스타일: {SID}`.
- 공통 프론트 부품은 `11-프론트부품.md`로만 쓰고 소스(`components/`·`hooks/`)를 통독하지 않는다. 부품을 새로 만들거나 바꾸면 11을 고친다.

**진행**
- 세션 하나에 ID 최대 3개. ID는 순서대로 하나씩 끝까지 마친다. 큰 화면(탭 3개+, 팝업 다수, 공통 부품 신설)은 단독.
- 결과는 확인한 것만 적는다. 못 한 것은 `미확인`과 이유.

## 2. 절차 (화면 하나)

| 단계 | 하는 일 |
|:---|:---|
| 분석 | `yunhee analysis screen <화면> --list` → 이벤트·버튼 `--class <클래스> --section events\|buttons` → `analysis grid <클래스>` → `analysis method <클래스>.<메서드>`(서버는 `--server`, 원문은 `-o code`) → `analysis sql <ns.id>`(`-o sql`) → `analysis model` → `yunhee table`. 색인이 없는 화면(메뉴 없음)은 소스 직접 분석으로 나온다 |
| 백엔드 | AS-IS 서버 클래스 1개 → `biz.{도메인}`의 `{Domain}{Resource}Controller/Service/Mapper` 1벌. `port-sql`로 조회 매퍼·DTO, `port-save`로 저장 조각(열 이름은 `yunhee table`과 맞춘다). 매퍼는 컴파일 전에 `yunhee sql-check --tobe backend/src/main/resources/mapper`. 매퍼 statement 위에 `<!-- AS-IS {sqlId} L{줄} (IDMS-IC) -->` |
| 프론트 | 그리드는 `grid-style.md`, 버튼은 `button-types.md` 이름만. 이벤트 핸들러 위에 `// [E3] retrieveButton[조회].Select (L55)`, 안 하면 `// [E3 생략] 사유`. `pages/screens.ts`에 메뉴 키(`sys06_class_nm`, 오타 그대로) 등록. 첫 주석 `[화면번호] 메뉴 경로` + AS-IS 경로 |
| 확인 | 아래 3절 |
| 기록 | `01*-변환목록.md`(또는 미변환 목록)의 상태 칸을 바꾼다. 메뉴가 있는 화면은 `yunhee drift --record <클래스> --id <ID>`. 필요하면 코드 주석에 "AS-IS와 다른 점"을 남긴다. 커밋 메시지에 ID와 요지 |

상태: `대기` → `완료`, 또는 `보류`(사유). 다음 작업은 목록에서 `대기`인 첫 줄.

## 3. 확인 (한 줄씩, 해당 없으면 건너뜀)

1. `yunhee run "./bm.sh compile"`, 테스트 · `yunhee run "npx tsc -b --noEmit"`(frontend에서)
2. 조회 API = AS-IS SQL: `yunhee compare GET …`(회사는 `-c`와 `--param companyId=`를 맞춘다) 또는 로그인할 수 없는 사원이면 `yunhee mapper-run "<매퍼.xml>#<id>" --compare <ns.id> -p … --count`. 행 수 같고 필드가 그리드 컬럼을 포함.
3. 저장 API: 시험 행 등록 → 수정 → 삭제로 되돌린다. `yunhee api … --log`로 SQL·예외, 배포 뒤 `yunhee log errors --since-deploy`.
4. 이벤트·버튼·그리드 수가 AS-IS와 같다: `yunhee analysis ui <화면> --tobe frontend/src/pages/<도메인>`(색인 없는 화면은 `analysis screen`과 직접 대조). 모자라면 완료가 아니다.
5. 같은 클래스를 쓰는 메뉴가 둘 이상이면 메뉴마다 조건이 같은지, 모든 UPDATE/DELETE에 로그인 회사 조건이 있는지.
6. 브라우저 시험은 ID 변환 중에 하지 않는다(방법은 `테스트` 작업에서 정립). RD 출력은 `tools/run-rd-server.sh status`→`start` 후 `calls [mrd]`로 mrd·rv 확인, 알림은 `tools/run-notice-server.sh`.
7. 끝: `yunhee trace-pair '#<메뉴번호>'`, `yunhee trace-crud --screen <클래스>`(`unresolved`·`⚠`는 오탐일 수 있어 직접 확인 — 0.8.4의 오탐 두 가지는 0.8.5에서 해결 — `05b` 0.8.5).

## 4. AS-IS → TOBE 대응

| 구분 | AS-IS | TOBE |
|:---|:---|:---|
| 화면 파일 | `client/vi/{dom}/{클래스}.java` | `frontend/src/pages/{dom}/{클래스}.tsx`, 컴포넌트 이름=클래스, 함수 이름=AS-IS 메서드 |
| 그리드 | `GridBuilder.addText(…)` | `analysis grid` 그대로 `gb.text('x', 200, '제목', { editor:'text' })`. 주석 처리된 컬럼은 넣지 않는다 |
| 버튼 | `new ColorButtonBar("조회")` | `<Button type="search">조회</Button>` (antd `Button` 쓰지 않는다) |
| 조회 | `GridRetrieveData.retrieve("dom.Cls.sel")` | `GET /api/v1/{dom}/{resource}` → `ApiResponse<List<…Res>>`, resource는 테이블 복수형 |
| 세션 값 | 클라이언트가 `LoginUser.getCompanyId()` 전송 | 서버가 `@AuthenticationPrincipal UserPrincipal`에서 꺼낸다 |
| LIKE | 클라이언트가 `"%"+값+"%"` | 서버 서비스가 만든다(null이면 `%%`) |
| 저장 | `UpdateDataModel` 동적 INSERT/UPDATE | `PUT` 변경 행 목록 → 행마다 명시 INSERT/UPDATE(화면이 바꾸는 컬럼만) → `selectById`로 다시 읽어 요청 순서대로 반환, `@Transactional`. ID≤0이면 `f_create_seq()` |
| 삭제 | `GridDeleteData` | `DELETE` body ID 목록, WHERE에 `company_id = 로그인 회사` |
| 불리언 열 | `'true'/'false'` 글자 | SQL에서 `(열='true')`로 읽고 `COALESCE(값,false)`로 쓴다. null 파라미터는 `jdbcType=BOOLEAN` |
| 15자리 넘는 Long ID | JS가 2^53 넘으면 값이 겹친다 | 그 DTO의 ID만 `ToStringSerializer`, TS 타입 `string` |
| 소수 계산 열 | 모델 `Long` | `BigDecimal`로 받는다 |
| 같은 모델을 여러 SQL이 공유 | | 열이 다르면 SQL마다 record를 나눈다(필드 누락=런타임 500) |
| 다른 화면 탭 열기 | `TempData` + `MenuOpener` | `openMenuByNo('1011')` + `TempData.publish/subscribe` |
| 화면 분할 | 비율·고정 크기 | 2단까지(3단 분할 없음) |

**그리드 CRUD 동작** (`useGridCrud`가 원본과 같게 동작한다):
- 조회: 목록을 바꾸고 저장 안 한 변경은 묻지 않고 버린다. 행 추가: DB에 쓰지 않고 변경도 아니다(입력 없이 저장하면 아무 일 없고 새 행은 다음 조회 때 사라진다).
- 저장: 변경 행만, 0건이면 서버도 안 부르고 메시지도 없다. 삭제: 저장된 행만 서버로, 임시 행은 화면에서만 뺀다.
- 일부러 원본과 다른 것: 저장·삭제 성공 메시지, 선택 없이 삭제하면 경고만 하고 서버를 부르지 않는다.

## 5. yunhee 사용 (원문·로그를 읽기 전에 줄일 수 있는지 먼저)

기준 버전 0.8.5. 시작에 `yunhee --version`, 높으면 `yunhee changelog --since 0.8.5`. 막히면 `yunhee <명령> --help`, 버전별 한계는 `05b-yunhee-버전이력.md`. 모두 `AssetERP/`에서 실행한다.

| 하려는 일 | 명령 |
|:---|:---|
| 화면 한눈에(번호로) | `yunhee screen-desc <번호,번호…> -s`(메뉴·TOBE 파일·버튼·그리드·팝업·API·SQL·테이블·AS-IS 서비스·이벤트) |
| TOBE 코드 위치 | `yunhee outline <파일…>` → 필요한 줄만 `yunhee cat 파일:시작-끝` |
| 참고 TOBE 화면 요약 | `yunhee analysis tobe <파일>` |
| 테이블 / DB 데이터 | `yunhee table <이름>`(스냅샷, 새 테이블은 없을 수 있음) / `yunhee sql "<SELECT>"`(읽기 전용, 쓰기 시험은 `-f x.sql --rollback`) |
| 빌드·배포 | `yunhee run "./bm.sh compile"`, `"./fm.sh compile"`, `"./deploy.sh"`(약 90초, 완료 알림을 기다린다). 실패는 `yunhee analysis run last --stdout\|--tests` |
| API 확인 | `yunhee api GET <경로> -p k=v -c <회사코드> --log`(고객사 관리자는 `-c kfstest`, `-c`만으로 그 회사 주소). 쓰기는 `-b '<json>'`, 행 수 변화는 `--track <테이블,…>`. 응답 줄이기 `--fields a,b`·`--where k=v`·`--count-by k`. 배포 직후 404면 몇 초 뒤 |
| 서버 로그 | `yunhee log errors --since-deploy`, `log tail --since 5m`, `log req <METHOD> <경로> -n 5 --trace`(출력은 UTC) |
| 원본 변경 | `tools/check-git.sh`, `yunhee drift --all --done-only --base baseline`, `drift <화면> -o diff` |

**쓰지 않는 것**: `cat`/`sed`/`head`/`tail`로 원본·색인·TOBE 소스 열기(훅이 막는다), `psql` 직접, `docker logs`, 셸에서 직접 gradle/npm, `grep -A/-B/-C`(대신 `yunhee grep`·`yunhee cat 파일:줄`). 막히면 우회하지 말고 yunhee로 다시 한다.

**자주 틀리는 것**: `CLAUDE.md`의 "에이전트 실수 목록"을 본다.

## 6. 고정 경로

- AS-IS 원본 `~/work/IDMS-IC` (`application/src/main/java/myApp`), 색인 `docs/as-is/src`(`menus.md`→`sys/screens/{클래스}.md`), `docs/as-is/db`, `docs/as-is/menus.tsv`. 저장소 루트의 `docs/as-is/`는 OMS 색인이니 섞지 않는다. 색인 만드는 법은 `CLAUDE.md`.
- 이름표: `docs/grid-style.md`, `docs/button-types.md`, 화면 유형 `docs/page-style.md`(해당 SID 절만), 공통 부품 `11-프론트부품.md`(프론트일 때), UX보강 `10-UX보강.md`.
