# 변경반영

AS-IS AssetERP는 유지보수 중이라 소스와 DB가 계속 바뀐다. 변환이 끝난 TOBE도 그 변경을 찾아 반영해야 한다.
Strangler Fig로 AS-IS와 TOBE가 함께 서비스된다고 가정하므로 **며칠 늦는 것은 괜찮지만 빠지는 것은 안 된다.**
빠지지 않게 하는 장치가 이 폴더의 **변경반영 대장**(`변경반영-대장.md`)이다.

## 파일

| 파일 | 내용 |
|:---|:---|
| `README.md` | 이 문서 — 원칙·절차·도구 |
| `변경반영-대장.md` | AS-IS 변경 한 건 = 한 줄. 상태를 끝까지 추적한다 |
| `../../tools/make-change-docs.sh` | `check-git.sh` 다음에 돌려 대장을 만든다(이어 붙임). 처리는 `../../tools/make_change_docs.py` |

## 원칙

1. **반영 단위는 화면이 아니라 "AS-IS에서 바뀐 것"이다.** 한 건 = 파일 하나의 SQL ID 하나 또는 메서드 하나(화면 클래스는 UI 변경 묶음 하나). 판단은 한 번만 하고, 영향받는 화면은 그 결과를 따른다.
   - 근거(2026-11-11 측정, 완료 화면 421개): `drift --done-only --base baseline`에서 "변경" 271개 중 **239개는 공통 파일 때문**이었고 자기 파일이 바뀐 화면은 32개뿐. 실제로 바뀐 파일은 129개(`Sys99_Print.java` 하나가 95화면, `apr01_appr.xml`·`Apr01_Appr.java`·`Sys00_Common.java`가 각 약 90화면).
   - 공통 파일이 바뀌어도 **그 화면이 쓰는 메서드·SQL이 안 바뀌었으면 해당없음**이다.
2. **업무 로직은 원본을 따르고, 화면 모양은 TOBE를 지킨다.** SQL·검사·메시지 조건·트랜잭션은 AS-IS대로 옮긴다. UX보강(`../1-변환/10-UX보강.md` UX-01~), 재설계(`../4-재설계/`), 화면별 사용자 지시로 **의도해서 다르게 한 부분은 원본대로 되돌리지 않는다.** 재설계한 화면은 로직만 반영한다.
3. **위험이 큰 종류부터** 처리한다: DB 구조 → SQL → 서버 로직 → 화면 → 새 화면.
4. **확인 없는 반영은 반영이 아니다.** 변경반영은 이미 돌아가는 화면을 고치는 일이라 망가뜨리기 쉽다. 아래 "반영 완료 조건"을 채워야 `반영`으로 바꾼다. 반영 한 건마다 테스트·대조가 하나씩 쌓이게 해서, 할수록 안전망이 두꺼워지게 한다. 묶음이 끝나면 기준선(`docs/baseline.json`)을 옮겨 같은 변경이 다시 뜨지 않게 한다.
5. 반영 코드는 `../1-변환/변환-가이드.md`의 규칙(패키지·네이밍·yunhee 사용)을 그대로 따른다. 커밋 메시지에 대장 키(`CH-…`)를 쓴다.

## 종류

| 종류 | 무엇 | 확인 도구(지금) | 반영 |
|:---|:---|:---|:---|
| `DB` | 테이블·열·함수·트리거 | `tools/check-git.sh --db-index`, `yunhee sql`(information_schema·`pg_proc`), `yunhee table` | 가장 먼저. 같은 DB를 쓰므로 TOBE SQL이 바로 깨질 수 있다. 열 추가·이름 변경이면 TOBE 매퍼·DTO 확인. **함수**는 AS-IS `doc/dbSource/*.sql`과 `pg_proc.prosrc`를 대조 → 다르면 `tools/db_dump_backup.sh` 백업 → 트랜잭션으로 묶은 SQL 파일(돌려주는 형식이 바뀌면 `DROP FUNCTION IF EXISTS` 먼저, 로컬에 없는 계정 GRANT는 뺌)을 **사용자가** `! docker exec -i <컨테이너> psql -U kdy987 -d asseterpdb -X -q < 파일`로 실행(yunhee는 DDL을 막고, 에이전트의 psql 직접 실행은 훅이 막는다) → 그 함수를 쓰는 TOBE 테스트를 돌린다(처음 사례 CH-0001~0003) |
| `SQL` | 매퍼 XML의 SQL ID | `yunhee analysis sql <ns.id>`, AS-IS `git diff` | `yunhee port-sql`로 다시 옮기고 `sql-check --tobe`·`compare`·`mapper-run --compare`로 결과 대조 |
| `LOGIC` | 서버 Java 메서드(검사·분기·메시지·호출 순서) | `yunhee analysis method <클래스>.<메서드> -o code` | TOBE 서비스·컨트롤러에 옮김. 업무 테스트(`5-테스트`)가 있으면 늘린다 |
| `MODEL` | 모델·DTO 필드 | `analysis model` | TOBE record·TS 타입에 필드 추가 |
| `UI` | 화면 클래스(위젯·그리드 컬럼·버튼·이벤트·메시지) | `yunhee drift <화면> -o diff`, `analysis ui <화면> --tobe …` | 버튼·컬럼·이벤트를 반영. 모양은 TOBE 부품 규칙대로 |
| `NEW` | 새 화면·메뉴·서버 메서드 | `yunhee drift --all --new`, `sys06_menu` | 대장에는 기록만 하고 변환 작업(`1-변환` 변환목록 새 ID)으로 넘긴다 |
| `ETC` | 빌드·설정·주석·공백 | — | 대부분 해당없음 |

## 상태

| 상태 | 뜻 |
|:---|:---|
| `대기` | 찾았고 아직 판단 전 |
| `해당없음` | 반영할 것이 없음 — 이유를 비고에 (예: 이 화면이 안 쓰는 SQL, TOBE에 없는 기능, 주석·공백만, 미변환 화면) |
| `반영` | TOBE에 옮기고 **확인까지 함** — `확인` 칸(무엇으로 확인했나)·처리일·TOBE 파일·커밋. `확인`이 비면 `make-change-docs.sh`가 경고한다 |
| `보류` | 사용자 결정 필요 또는 다른 작업 뒤 — 이유를 비고에 |
| `넘김` | 다른 작업으로 보냄(`NEW` → 변환, 설계가 바뀌는 것 → 재설계) |

## 반영 완료 조건

AS-IS와 TOBE가 같은 DB(asseterpdb)를 쓰므로 **AS-IS가 정답지**다. 기대값을 손으로 쓰지 않고 "AS-IS와 같은 결과인가"로 확인할 수 있다.

| 언제 | 무엇 | 도구 | 대장 `확인` 칸에 |
|:---|:---|:---|:---|
| 고치기 전 | 그 도메인의 기존 테스트가 통과하는지(출발점이 초록이어야 고친 뒤 비교가 된다) | `yunhee run "gradle test --tests '*Emp*'"` | — |
| 고친 뒤 · `SQL` | AS-IS SQL과 TOBE 매퍼 결과가 같은지(건수·값). 분기 있는 조회는 파라미터 조합마다 | `yunhee compare`, `yunhee mapper-run "<매퍼>#<id>" --compare <ns.id> -p … --count`(쓰기는 `--rollback`) | `compare 일치(3조합)` |
| 고친 뒤 · `LOGIC` | 바뀐 규칙(검사·분기·메시지)을 테스트 하나로 고정. 없던 테스트면 새로 | 기존 `*DbTest`(롤백) 방식, `yunhee run "gradle test --tests '<클래스>'"` | 테스트 클래스 이름 |
| 고친 뒤 · `MODEL`·API | 새 필드가 응답에 실려 오는지 | `yunhee api … --log` | `api 200·필드 확인` |
| 고친 뒤 · `UI` | 화면이 열리고 조회되는지, 바뀐 버튼·컬럼 | `tools/screen-test/list.cjs`(열기·조회), 사용자 확인(5173) | `화면 확인(사용자)` 또는 `list.cjs 통과` |
| 커밋 | **대장 키 하나 = 커밋 하나**(메시지에 `CH-…`). 문제가 생기면 그 커밋만 되돌린다 | `git revert <커밋>` | — |
| 정기(주 1회·큰 묶음 뒤) | 전체 테스트 + 정적분석 | `yunhee run "gradle test"`, `tools/code-health.sh` | — |

- `해당없음`·`보류`·`넘김`은 `확인` 칸이 없어도 된다(비고에 이유).
- 한계: 화면 모양, 여러 화면을 거치는 업무 흐름(결재 등)은 이것만으로 다 못 잡는다 — `2-업무분석` 시나리오를 `5-테스트`에서 자동화해 채운다.

## 절차

### 매일 (자동으로 돌릴 수 있는 단계 — 사람 판단 없음)

```bash
cd AssetERP
tools/check-git.sh                 # AS-IS pull → 색인 다시 만들기 (DB가 바뀌었으면 --db-index)
tools/make-change-docs.sh --dry-run   # 무엇이 새로 붙을지 보기
tools/make-change-docs.sh          # 변경반영-대장에 이어 붙임 → "새 줄 n · 대기 줄 갱신 m"
```
- `make-change-docs.sh`가 하는 일: `yunhee drift --all --done-only --base baseline -o json` → 바뀐 파일을 SQL ID·메서드 단위로 나눔 → 색인·AS-IS 호출(`mapperName + ".id"`, `<include refid>`, 클라이언트 서비스 문자열)을 따라 쓰는 완료 화면 → TOBE 대응 후보 → 기준선 이후 새 파일·DB 스크립트 → 대장에 이어 붙임.
- **처리한 줄(반영·해당없음·보류·넘김)은 건드리지 않는다.** 같은 단위가 `대기`면 커밋·변경 요약·영향 화면만 고치고, 처리한 단위가 그 뒤 커밋으로 다시 바뀌었으면 새 줄. 키는 마지막 `CH-` 번호에서 이어 간다.
- `--reuse`는 drift를 다시 돌리지 않고 지난 결과(`.yunhee/drift-today.json`)를 쓴다.
- ntfy로 `대기` 건수를 알린다.

### 주 1~2회 (묶음 처리)

1. `대기`를 종류 순서(DB → SQL → LOGIC → MODEL → UI → NEW)로 본다.
2. 한 건마다:
   1. AS-IS diff를 SQL ID·메서드 범위로 본다.
   2. 그 단위를 쓰는 화면(화면번호)과 TOBE 대응(매퍼 id·서비스 메서드·tsx)을 찾는다. 대응 찾기는 `yunhee trace-pair '#번호'`.
   3. 해당없음이면 이유를 적고 끝낸다.
   4. 반영이면: 기존 테스트 통과 확인 → TOBE를 고친다 → "반영 완료 조건"대로 확인 → `확인` 칸을 채우고 상태 `반영` → 그 키 하나로 커밋.
3. 묶음이 끝나면 영향 화면의 기준을 옮긴다: `yunhee drift --record <클래스…>`. 공통 파일 하나에 화면이 많으면 대장의 영향 화면 목록 전부(지금 기준선이 화면 단위라서 — "도구" 2번).
4. 커밋 메시지에 대장 키, 사용자에게 확인할 화면 목록(화면번호 · 메뉴 경로 · 확인할 동작)을 보고한다.

### 길게 보면

메뉴를 TOBE로 완전히 넘기면(전환), 그 메뉴는 AS-IS에서 더 고치지 않고 TOBE에서 고치도록 AS-IS 개발 쪽과 약속한다. 그래야 변경반영이 줄어드는 쪽으로 간다. 전환 단위·공존·롤백 문서(재설계 작업에서 정할 것)에 같이 넣는다.

## 도구

지금은 `tools/check-git.sh`(pull·색인), `yunhee drift`(화면 단위 감지), 그 위에서 단위로 나누는 임시 도구 `tools/make-change-docs.sh`다.
yunhee에 **`drift-` 명령군**을 제안했다(`~/work/yunhee-cli/docs/수정사항/수정사항054.md`). `trace-*`가 업무분석용이듯 `drift-*`는 변경반영용이다.

| 명령(제안) | 하는 일 | 대장에서 쓰는 곳 |
|:---|:---|:---|
| `drift-log` | 기준 이후 AS-IS 커밋과 파일, 종류(DB·SQL·LOGIC·MODEL·UI·ETC) | 매일 — 무엇이 들어왔나 |
| `drift-unit` | 바뀐 파일을 **SQL ID·메서드 단위**로 쪼개고, 단위마다 쓰는 화면(화면번호)과 TOBE 대응 | 매일 — 대장 한 줄의 재료, 공통 파일 잡음 제거 |
| `drift-list` | `drift-unit` 결과를 대장에 `대기`로 덧붙임(이미 있는 키는 건너뜀) | 매일 — 지금의 `make-change-docs.sh` |
| `drift-diff <단위>` | 한 단위의 AS-IS 전후 + 지금 TOBE 대응을 나란히 | 묶음 — 반영 판단 |
| `drift-db` | DB 스냅샷(dbml) 전후의 테이블·열·함수 차이와 그것을 쓰는 TOBE 매퍼 | 묶음 — `DB` 종류 |
| `drift-done <키…>` | 대장 상태를 바꾸고 **파일·단위 기준선**을 옮김(그 단위를 쓰는 화면 모두) | 묶음 끝 — `--record` 화면별 반복 없앰 |

도구가 생기면 `make-change-docs.sh` 안을 `drift-unit`·`drift-list` 두 줄로 바꾼다.

## 연결되는 다른 작업

- **변환**: 반영 규칙은 `../1-변환/변환-가이드.md`, 새 화면(`NEW`)은 변환목록 새 ID로 넘긴다.
- **업무분석**: 바뀐 SQL·로직이 업무 흐름을 바꾸면 `../2-업무분석/`의 시나리오도 고친다.
- **재설계**: 재설계한 화면은 로직만 반영. 전환 단위·공존·롤백 문서는 재설계에서 정한다.
- **테스트**: 반영한 업무는 `../5-테스트/`의 테스트로 확인하고, 없으면 하나 늘린다.
