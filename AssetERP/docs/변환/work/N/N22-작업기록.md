## 결정 (사용자 확인 필요)
- **증빙자료 창(`Tdm00_Lookup_RelateAppr`)을 이번에 만들지 않았다.** 이 창은 `Com01_Lookup_RelateAppr`의 연결문서(전자결재 문서 불러오기·`Apr01_Edit_ApprDoc`으로 신규 문서 작성)와 업로드 파일 그리드, 외부보관 증빙 CRUD를 한 창에 묶은 것이고, `Apr01_Edit_ApprDoc`(5831줄)이 TOBE에 없다(결재 편집창은 N11~N20과 같이 안내만 한다는 방침). 그래서 점검상세의 [증빙자료(n건)]와 일괄점검의 [증빙자료]는 안내 메시지만 띄운다. **그 결과 증빙 필수 설정(`tdm91_evid_file_check_yn` = true, 설정이 없을 때의 기본값도 true)인 기간의 점검은 "적정"으로 점검완료가 안 된다** — 증빙을 올릴 창이 없기 때문이다(미흡·개선·해당없음은 영향 없음). 2단계를 별도 ID로 둘지(연결문서 포함 전체 / 업로드·외부보관 증빙만 먼저), 순서는 사용자가 정한다.
- **[AI] 점검의견 자동 작성은 연결하지 않았다.** 서버 `getBotCheckCmnt`가 `BotService`로 외부 AI 서버(`botUrl`)에 POST한다. 주소·인증 설정이 이 프로젝트에 없어 안내만. 연결한다면 설정 키와 호출 방식을 사용자가 정해야 한다.
- **`updateComplete`의 상태 판단은 서버가 읽은 값으로 한다.** AS-IS는 완료취소(C)에서 화면이 보낸 `checkStatusCode`를 썼다. 화면은 읽기 전용으로 DB 값을 보여 주는 채라 같은 값이다. 완료취소의 점검일·결과·의견도 화면 값이 아니라 DB 값을 그대로 둔다(AS-IS는 화면 값 = 같은 값을 다시 쓴다).
- **이력(`tdm55`)의 처리결과 이름은 AS-IS처럼 화면 콤보의 글자를 받는다**(점검상세 콤보는 `TdmCheckResult0001`, 일괄점검 콤보는 `TdmCheckResult0003`). 같은 코드의 이름이 두 코드 그룹에서 달라질 수 있어 서버가 코드로 다시 찾지 않았다. 일괄취소는 AS-IS처럼 의견을 null로 남긴다(`setCheckCmnt(null)` 뒤에 이력을 쓰는 순서).
- **점검자(`personId`)는 요청 값을 쓴다.** 점검시작·시작취소의 처리자도 화면의 점검자(= 책무담당자가 대신 작업할 때 선택한 사원)다 — AS-IS 그대로(보안 제안 참고).
- 점검시작 대상 조회(`selectCheckTargetByCheckerId`)는 행 통째가 아니라 ID만 받는다(서버가 쓰는 것은 ID뿐).
- `tdm91_company_setup.selectByDate`의 "기본 행"(설정이 없을 때 `2026-01-01` 이후에만 보이는 가짜 행)을 그대로 옮겼다. 점검 시작일이 2026-01-01 이전이고 설정이 없으면 AS-IS는 `NullPointerException`인데 TOBE는 기본값(증빙 필수·글자수 제한 없음)으로 처리한다(방어).

## 확인 필요 (코드 해석)
- **묶음 헤더 "점검결과"**: `HeaderGroupMap(0, 5, HeaderGroupConfig(…, 1, 3))`를 행번호 0번 포함 읽기(N21 확정 읽기)로 5·6·7번 열 = 적정·미흡·해당없음으로 걸었다. 점검건수(4번 열)는 묶음 밖이다. 이름만 보면 점검건수도 "점검결과"에 들어갈 법해서 브라우저 일괄 시험에서 AS-IS 화면과 같이 본다.
- `Tdm52_TabPage_CheckManl.buildGrid`의 `addDynamicCell(…checkStatusCode, 45, "점검", actionCell01, true)`: 마지막 `true`를 "점검상태가 null이면 아이콘을 안 그림"으로 읽었다(원본 주석: "점검버튼 그리드에서 비활성화(DynamicCell적용)"). 브라우저에서 확인.
- 조회 직후 목록에서 첫 행을 `select(0, false)`하는데 체크박스 선택 모델이라 첫 행이 **체크된** 채로 시작한다. TOBE도 첫 행을 선택(체크)한다 — [일괄점검]을 누르면 그 행이 포함된다(AS-IS도 같은 모양으로 보이나 브라우저에서 확인).

## 제안 (승인 대기)
- (보안) 점검자 `personId`·`chckOrgId`를 서버가 검증하지 않는다 — 책무담당자가 아닌 사용자도 API로 다른 사원의 점검을 시작·취소할 수 있다(AS-IS도 같다. 화면에서만 점검자 칸 비활성). 서버에서 `checkIsManager` 또는 `personId = 로그인 사용자`만 허용하면 막힌다.
- (보안/정합) `batchCheckComplete`·`batchCancelComplete`·`updateCheckStatus`는 점검항목의 현재 상태를 서버가 확인하지 않는다(화면이 걸러 준 값을 믿음). 승인요청(20)·진행(21)·완료(25) 항목도 API로 점검완료로 되돌릴 수 있다. 서버에서 일괄점검은 11, 일괄취소는 19만 허용하면 막힌다.
- (UX) 일괄점검 창에는 대상 건수가 보이지 않는다. 확인 단계에서 건수를 이미 알려 주므로 불필요할 수 있다.
- (부품) 화면에서 같은 코드를 두 번째로 썼다: 부서 점검현황 그리드의 `cnt()` 건수 렌더러(N21·N22). 세 번째가 나오면(N23?) 공통 부품으로 뽑을 후보.
