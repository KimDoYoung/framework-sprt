## 1단계에서 정한 것·AS-IS와 다른 점 (사용자 확인용)
1. **ICAM 제외 범위**: 최초업무시작일 보정(01)·ICAM 발생보수 읽기→`biz21` 보수상세 생성(03)을 옮기지 않았다. 그래서 새로 만든 자료의 **발생보수는 0**이고 최저·병행·청구보수만 계산된다(기존 AS-IS 자료는 발생보수가 들어 있음). 이 구간은 코드 주석 `ICAM … 옮기지 않았다`로 표시.
2. **결함 의심 1번 적용**: `deleteTermLastCloseDate`에 `biz22_cont_corp_id`·`biz22_charge_date` 조건을 더했다(승인된 원칙 4 예외, 원래 SQL은 매퍼 주석). 테스트 `계약사별_자료생성은_그_계약사_구간만_다시_만든다`가 다른 계약사 구간이 그대로임을 본다.
3. **실패 처리**: AS-IS `result.fail(-1,…)`(확정됨·운영구분 없음)을 TOBE는 `BusinessException`(INVALID_INPUT)으로 던져 그 자료생성 **전체를 되돌린다**(AS-IS는 그때까지의 변경이 남는지 확인하지 못함 — 제안: 같은 동작이면 문제 없음).
4. **회사 조건 추가**: 한 건 조회·삭제·확정·상신ID·계산상세·계좌에 `company_id` 조건을 더했다(다른 회사 행 접근 차단, 결과는 같음).
5. **편집창 저장**: `UpdateDataModel`처럼 번호가 있으면 UPDATE·없으면 INSERT. 쓰는 열은 편집창이 바꾸는 청구일자·운용사·계약사·발생보수·청구보수·세금·비고 + 청구대상(청구보수가 비었거나 0이면 `false`). 새 행의 확정여부는 `'false'`(AS-IS는 null일 수 있고 목록은 둘 다 미확정으로 읽음). 같은 운용사·분기 중복 검사(`updateCheck`)는 AS-IS처럼 따로 호출한다(`same-corp-count`, 0이면 저장).
6. **삭제의 확정 검사**는 AS-IS처럼 화면에서 한다(서버 `deleteList`는 검사 없음). `confirmUpdate`의 "전표 `trId`가 있으면 취소 불가"도 화면 몫.
7. 목록 그리드 열 `fixYnName`은 응답 필드 `fixNm`(SQL 열 `biz20_fix_nm`)이다. 계산상세·출력용 모델은 `BizFeeChargeCalc`(필드 공개 클래스, 자료생성이 구간 값을 채워 넣는 작업 모델).
8. `Biz10_Lookup_ContCorp`는 EE20 `GET /api/v1/biz/cont-corps`를 그대로 쓴다(새 API 없음). 파일 창은 공통 `fileApi(parentId)` 재사용.
