## 공통 절차와 다른 점
- **승인 판정은 서버도 본다(보안 보강)**: 화면은 내 차례인 결재자에게만 [승인]·[반려]를 켜므로 같은 조건(`stepEmpId = 로그인 사원`)을 `decision`에서, 결재의견·반려사유는 `apprEmpId = 로그인 사원`을 `note`에서 서버가 검사한다(어기면 403). 원본 서버에는 없다.
- **승인·반려 + 의뢰 승인상태를 한 호출로**: 원본은 클라이언트가 `modelUpdate`와 `Sr.update`를 이어 부른다. 마지막 결재자 여부(`last`)는 화면이 보내고 서버가 한 트랜잭션으로 처리한다.
- **결재선 그리드 정렬**: 원본 `buildApprStepGrid`는 store에 결재상태(`stepStatusCode`) 정렬을 걸지만, 내 차례 판정이 "앞 결재자 승인 + 나 대기"의 **결재순(seq)** 을 쓰므로 서버가 주는 `seq` 순서 그대로 보인다. 원본의 실제 표시 순서는 미확인(작업기록).
- **요청내용 저장**: 원본은 `getHtmlText().replaceAll("'", "''")`로 따옴표를 겹쳐 보낸다(문자열 합치기용 흔적). 여기는 값을 그대로 저장한다(바인딩 변수).
- `Scm02_Edit_ApprStep`은 `Apr04_Edit_ApprStep`을 재사용하지 않고 따로 뒀다 — 줄 타입(결재선 `00`~`30`)과 모델이 다르고, 검색·최근결재선·참조등록·인감·잠금이 없다.
- [삭제]에 선택이 없으면 원본은 오류가 난다 → "삭제할 개발의뢰를 선택해주세요" 안내만 더했다.
