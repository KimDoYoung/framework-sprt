## SQL 이식
| SQL ID | 테이블 | 그대로 / 수정 |
|:---|:---|:---|
| selectByIfType · selectById | ifi90_config | 그대로(열 별칭만). **`ifi90_target_key` → `ifi90_target_key1`** (아래). `sql-check --tobe` 7/7 통과 |
| checkConfigId | ifi91_config_api, ifi95_config_file | 그대로 |
| 저장·삭제·채번 | ifi90_config | UpdateDataModel의 동적 SQL을 명시 SQL로(`yunhee port-save` 틀을 열 이름 직접 수정) |

- **원본 SQL이 이 DB에서 안 맞는 곳(03 원칙 4 예외)**: 원본 모델·resultMap은 `ifi90_target_key`인데 asseterpdb `ifi90_config`에는 `ifi90_target_key1`·`ifi90_target_key2`만 있다. 원본 UpdateDataModel은 DB 컬럼 목록에 있는 것만 쓰므로 이 DB에서는 Target Key가 읽히지도 저장되지도 않는다(`ifi90_config.*`에 없음). **사용자 결정(2026-10-17)**: `targetKey ↔ ifi90_target_key1`로 읽고 쓴다.
- **계정PW 저장(원본 동작 그대로)**: 편집 폼·그리드는 복호화 값(`localPwDec`·`targetPwDec` = `to_decrypts(ifi90_*_pw)`)을 보이고 고친다. 그러나 원본 UpdateDataModel은 `*_pw_dec`가 테이블 컬럼이 아니라 쓰지 않고, 암호화 컬럼 `*_pw`는 읽어 온 값(`localPw`)을 그대로 되쓴다 → **폼에서 계정PW를 고쳐도 저장되지 않는다**. TOBE도 같게 INSERT/UPDATE에서 `*_pw` 열을 빼고(신규 행은 NULL, 수정은 그대로 둠) 요청에 PW를 받지 않는다. 제안은 작업기록.
