# 06. 결과확인

작업물이 맞게 됐는지 **무엇을, 어떻게, 어떤 기준으로** 확인하는지 적는다. 화면별 결과는 `work/{id}-결과확인.md`에 적고, 01에는 상태만 적는다.

## 결과 표기

- `통과`: 실제로 실행해서 기준을 만족했다. 증거(명령, 행 수, 비교 대상)를 같이 적는다.
- `실패`: 기준을 만족하지 못했다. 고칠 때까지 ID는 `완료`가 될 수 없다.
- `해당없음`: 그 화면에 없는 기능이다(예: 삭제 버튼이 없음).
- `미확인`: 확인하지 못했다. 이유를 적는다(03 원칙 11). 미확인이 남은 채로 `완료`하려면 사용자의 동의를 받는다.

| 4 | 저장 API | 같은 값 PUT, 또는 시험 행을 등록한 뒤 바로 삭제(03 원칙 2) | 성공 응답, 데이터가 원래와 같음 |
| 5 | 이벤트 누락 없음 | `{id}-작업방법`의 E-id 목록과 코드의 `// [E…]` 주석을 대조 | 모든 E-id가 구현되었거나 `[E… 생략] 사유` |

| 7 | 동작 | 조회 / 등록 / 수정 / 삭제 / 팝업 / 엑셀 등 화면에 있는 기능을 하나씩 실행 | 각 기능이 AS-IS 처리 순서·메시지대로 동작 |

| 9 | 메뉴 여러 개 | 같은 클래스를 쓰는 메뉴가 둘 이상이면 각 메뉴에서 연다 | 메뉴마다 AS-IS와 같은 조건으로 동작 |
| 10 | UI 대조표 (03 원칙 12) | 색인 화면 파일의 클래스마다(본 화면·하위 탭·팝업·조회창) `#### 사용된 버튼들` 수, `#### 이벤트` 수(└ 하위 이벤트 포함), 그리드 수·종류를 세어 TOBE와 표로 대조. 레이아웃(툴바 순서, 하위 탭, 분할)도 본다 | 모든 클래스가 같은 수. 다르면 이유(`[E… 생략]`, 다음 단계) |

## 확인 도구 (`AssetERP_1/tools/`)

| 도구 | 하는 일 | 쓰는 항목 |
|:---|:---|:---|
| `tools/menus.sh <base> <host:port> <user> <pass> <company>` | 로그인 → 메뉴 트리 1·2·3차 개수와 JSON 해시 → 로그아웃. 이전 회차 배포본과 같은 값인지 비교 | 8 권한·회사 (메뉴 노출) |
| `tools/smoke-frame.js <스크린샷 폴더> [base] [1차] [3차]` | 브라우저로 로그인 → MyPage → 메뉴 → 탭 열기, STOMP 연결, 콘솔 에러, 스크린샷 | 6 화면 구성, 7 동작(열기) |
| `tools/ui-count.sh <색인 화면 파일>` | 클래스마다 버튼·이벤트·그리드 수와 합계(UI 대조표의 AS-IS 쪽) | 10 UI 대조표 |
| `tools/screens/{id}.js <스크린샷 폴더> [base] [회사]` | 화면별 동작 확인(A01부터): 열기 → 조회 행 수·헤더 → 등록·저장 → 삭제, 메시지·확인 문구, 스크린샷. **실패해도 시험 행을 지우는 cleanup** 포함 | 6, 7 |

- 실제로 실행하면 여러 테이블에 데이터가 남는 기능(회사 등록 등)은 화면에서 실행하지 않는다. SQL은 DB 시험(`@MybatisTest`, 롤백)으로, 화면은 서버가 거절하는 입력(중복 등)으로 끝까지 보낸다(`tools/screens/A15.js`).
- 고객사 메뉴(admin 회사에 없는 메뉴)는 admin 테넌트 로그인 화면에서 회사(예: kfstest)를 골라 그 회사 관리자로 확인한다.

- 같은 계정으로 로그인하므로 그 계정의 다른 세션(예: 사용자가 열어 둔 화면)은 중복 로그인 차단으로 끊길 수 있다.
- 확인 항목을 더하거나 바꿔야 하면 이 표를 고치고, 고친 사실을 그 ID 작업기록에 남긴다.
