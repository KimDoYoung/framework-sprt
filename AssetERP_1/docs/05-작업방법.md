# 05. 작업방법

04의 각 작업을 **어떻게** 하는지 적는다. 모든 ID에 공통인 것만 여기에 두고, 화면마다 다른 것은 `work/{id}-작업방법.md`에 둔다.
명령은 저장소 루트(`framework-sprt/`)에서 실행한다. 도구 사용 규칙(`yunhee run/api/outline/table`, 원본은 색인이 가리키는 줄만 읽기)은 `../../CLAUDE.md`의 yunhee 절을 따르며 여기에 다시 적지 않는다.

## 0. ID 하나를 시작하고 끝내는 법 (B·A 공통)

1. 01에서 상태가 `대기`인 첫 ID를 고른다(04 순서). 01의 상태를 바꾼다.
2. `work/{id}-작업기록.md`를 만든다(§4 템플릿). A는 `work/{id}-작업방법.md`(§3)와 `work/{id}-결과확인.md`(06 템플릿)도 만든다.
3. 아래 절차대로 작업하면서, 한 일·막힌 점·결정을 작업기록에 바로 적는다.
4. 끝나면 비용을 정리한다(작업기록의 "비용" 절. 빌드·테스트 횟수와 실패 수는 `yunhee runs`에서 옮긴다). 01을 `완료`로 바꾼다.
5. 공통 절차를 바꿔야 했다면 이 문서나 06을 고치고, 그 사실을 작업기록에 남긴다(03 원칙 10).
6. 다음 회차에 도움이 될 교훈이 있으면 `08-회차인계.md`의 "교훈" 표에 한 줄 적는다.

### B01 명령

```bash
# 메뉴 TSV (asseterpdb sys06_menu, 경로·화면번호 포함)
psql -h localhost -U kdy987 -d asseterpdb -AtF $'\t' -c "
WITH RECURSIVE t AS (
  SELECT sys06_menu_id id, sys06_menu_nm::text path, sys06_seq::text sort FROM sys06_menu WHERE sys06_parent_id = 0
  UNION ALL
  SELECT m.sys06_menu_id, t.path || ' > ' || m.sys06_menu_nm, t.sort || '.' || coalesce(m.sys06_seq,'')
  FROM sys06_menu m JOIN t ON m.sys06_parent_id = t.id)
SELECT coalesce(m.sys06_menu_no,''), t.path, m.sys06_class_nm, coalesce(m.sys06_use_yn,'')
FROM t JOIN sys06_menu m ON m.sys06_menu_id = t.id
WHERE coalesce(m.sys06_class_nm,'') <> '' ORDER BY t.sort" > AssetERP_1/docs/as-is/menus.tsv

# DB 스키마가 바뀌었으면 먼저: yunhee dbml LOCAL_DB -o .yunhee/asseterp-dbml.md
yunhee index-db .yunhee/asseterp-dbml.md -t AssetERP_1/docs/as-is/db
yunhee index-src ~/oms-data/src/Asset-ERP -t AssetERP_1/docs/as-is/src   # menus.tsv·db는 -t의 상위 폴더에서 찾는다
```
- index-db를 다시 돌렸으면 index-src도 다시 돌린다(테이블 링크와 `⚠DB없음` 판정이 DB 색인을 쓴다).
- `-t`에는 색인 전용 폴더만 준다(실행할 때마다 그 아래 *.md를 지운다). 루트의 `docs/as-is/`는 OMS 색인이므로 쓰지 않는다.

## 6. AS-IS → TOBE 대응

OMS에서 정한 대응(`../../docs/OMS-convert.md`)은 참고만 하고, 이 원본에서 확인된 것만 옮겨 적는다.

상위 `../CLAUDE.md`의 yunhee 절이 기준이고, 이 절은 AssetERP_1에 맞춘 구체 사용법이다. **기준 버전 0.2.1** (수정사항 015·016 반영, 시험 결과는 08).

### 세션 시작
- `yunhee --version` → 이 절의 기준 버전보다 높으면 `yunhee changelog --since 0.2.1`로 **바뀐 것만** 읽고, 쓸 만한 기능이 생겼으면 이 절을 고친다(작업기록에 남김).
- yunhee가 바뀌어 색인 결과가 달라질 수 있으면 색인을 다시 만든다(§1 B01 명령).
- 사용법이 헷갈리면 `yunhee <명령> --help`. `yunhee agent-guide`는 처음 한 번만 읽는다(이 절과 다르면 이 절을 따른다).

### A 작업 단계별 명령
| 단계 | 하려는 일 | 쓰는 것 | 하지 않는 것 |
|:---|:---|:---|:---|
| 분석 | 화면 구성·이벤트·그리드·버튼 | 색인 화면 파일 `docs/as-is/src/sys/screens/{클래스}.md`의 `## UI`(클래스마다 이벤트·메서드 줄 범위·Grid Spec·버튼). 긴 파일은 `grep -n "^## \|^### "`로 절 위치를 본 뒤 필요한 절만 `sed -n` | 색인 전체 출력, `yunhee events` 재실행, `yunhee prepare` |
| 분석 | UI 대조표 AS-IS 쪽(06 항목 10) | `tools/ui-count.sh <색인 화면 파일>` | 손으로 세기 |
| 분석 | 저장이 무엇을 하는지 | 서비스 표의 `UpdateDataModel(테이블)` 표시와 **"저장 시 부수 효과" 절**(공용 저장 클래스 안의 테이블별 추가 SQL) | 저장 서비스 SQL이 `-`라고 "SQL 없음"으로 판단 |
| 분석 | 원본 처리 로직 | 색인이 가리키는 **메서드 줄 범위만** `sed -n 'a,bp'` | 원본 Java·매퍼 XML 통째로 |
| 분석 | AS-IS SQL 위치·정합성 | 색인 SQL 파일 `docs/as-is/src/{도메인}/sql/{매퍼}.md`(줄 번호, 같은 namespace 경고), `docs/as-is/sql-check.md` | 매퍼 XML 전체 열기 |
| 분석 | 테이블 구조 | `yunhee table <이름>` / `'<패턴>'` | `\d`·카탈로그, DBML 전체 |
| 분석 | DB 데이터(행 수·중복·기존 값) | `yunhee sql "<SELECT>"` (읽기 전용 강제, 5행만 표시 `--limit`) | psql 직접 |
| 분석 | 저장 SQL이 이 DB에서 도는지 | SQL 파일을 `yunhee sql -f x.sql --rollback` (항상 ROLLBACK, `\gset` 변수 가능, COMMIT·DDL 거부) | psql 트랜잭션 수동 |
| 백엔드 | 조회 SQL → 매퍼 조각·DTO | `yunhee port-sql <ns.sqlId> --cols <그리드 순서> --getter-defaults --package kr.co.kfs.asseterp.biz.{dom}.dto` → 복사 후 이름만 다듬는다 | 별칭·record 필드 손으로 쓰기 |
| 백엔드 | UpdateDataModel 저장 → 명시 SQL | `yunhee port-save <table> --cols <화면이 바꾸는 컬럼> --company-col <회사 컬럼>` (부수 효과 SQL·고정값·Mapper 메서드 목록 포함) | 저장·부수 효과 SQL 손으로 옮기기 |
| 백엔드 | 매퍼가 DB에서 도는지·DTO와 맞는지 | `yunhee sql-check --tobe backend/src/main/resources/mapper` — **컴파일·배포 전에** | 서버 띄워 API 호출로 오타 찾기 |
| 백엔드 | TOBE 코드 위치 | `yunhee outline <파일 또는 폴더>` → 필요한 줄만 Read(offset/limit) | 통째로 읽기 |
| 공통 | 빌드·테스트·배포 | `yunhee run "./bm.sh compile"`, `yunhee run "bash -c 'cd backend && gradle test'"`, `yunhee run "./fm.sh compile"`, `yunhee run "npx tsc -b --noEmit"`(frontend에서), `yunhee run "./deploy.sh"`. 실패하면 요약을 보고 더 필요하면 `.yunhee/runs/<id>.log`에서 그 부분만 grep | 셸 직접 실행 |
| 확인 | API 응답 | `yunhee api GET <경로> [-p k=v] [-c 회사]` | curl·fetch로 직접 로그인 |
| 확인 | 조회 API = AS-IS SQL(06 항목 3) | `yunhee compare GET <경로> [-p …] [-c 회사] --sql <ns.sqlId> --param k=v …` → `API rows=X, SQL rows=Y ✅ fields ⊇ grid cols ✅` | API와 psql 결과를 따로 세기 |
| 기록 | 실행 이력·비용 | `yunhee runs`, `yunhee last-run` → 작업기록 "비용" 표 | |

### `yunhee api`·`compare` — AssetERP_1에서 쓰는 값
- base: `.env.local`이 Tomcat 배포본 `http://localhost:8082/AssetERP_1`을 가리킨다(OMS 작업은 끝남, `.yunhee.toml` 두지 않음). 개발 서버(bootRun)를 볼 때만 `--base http://localhost:8080`.
- 응답 첫 줄 태그 `[AssetERP_1 · tenant=… · company=…]`로 어디를 불렀는지 확인한다.
- 회사: admin 회사(0)는 옵션 없이. **고객사 관리자는 `-c <회사코드>`**(테넌트 admin이 자동으로 붙는다. 예: `-c kfstest` → 11행).
- 저장 API 시험은 같은 값 PUT, 또는 시험 행 등록 후 바로 DELETE(03 원칙 2). 여러 테이블에 쓰는 저장(회사 등록 등)은 API로 하지 않고 `yunhee sql --rollback` + `@MybatisTest`로 확인한다.
- `compare`의 `--param`에는 서버가 세션에서 넣는 값(회사 ID 등)을 직접 준다.

### yunhee로 못 하는 것 (대안과 기록)
| 일 | 대안 | 줄이는 법 |
|:---|:---|:---|
| 브라우저 동작 확인 | `tools/screens/{id}.js` (06) | 결과를 JSON 몇 줄로 출력, 스크린샷은 실패했을 때만 본다 |
| 확인 스크립트의 시험 행 정리 | 스크립트 안의 fetch(실패해도 돌아야 해서) | |
| 프로젝트 밖 매퍼의 DTO 대조 | `sql-check --tobe`는 매퍼가 프로젝트 안에 있어야 DTO 소스를 찾는다(밖이면 안내 없이 대조 생략, 0.2.1) | 시험 매퍼는 `backend/src/main/resources/` 아래 임시 폴더에 두고 끝나면 지운다 |
- yunhee 대신 다른 방법을 쓴 경우는 `{id}-작업기록`에 **한 줄로 사유**를 남긴다. 같은 사유가 반복되면 yunhee 개선 제안으로 08에 적는다.

### 토큰을 아끼는 습관
- 같은 파일·색인을 다시 읽지 않는다. 앞에서 본 내용은 `{id}-작업방법`에 옮겨 적고 그것을 본다.
- 명령 출력은 `head`·`tail`·`grep`으로 필요한 줄만 받는다.
- 큰 화면(A15처럼 하위 클래스가 많은 것)은 클래스 하나씩 분석 → 작업방법에 기록 → 다음 클래스 순으로 한다.
- 기계적인 코드(매퍼 조각, record, 명시 저장 SQL)는 `port-sql`·`port-save` 결과를 복사해 고친다. 직접 쓰면 출력 토큰이 크다.
