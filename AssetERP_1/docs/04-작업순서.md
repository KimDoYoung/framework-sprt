# 04. 작업순서

무엇을 어떤 순서로 하는지만 적는다. 각 작업을 어떻게 하는지는 05, 상태는 01에 있다.

## 전체 순서

```
B01 색인 → B02 SQL 정합성 → B03 범위 확정
  → B04 골격 → B05 로그인 → B06 프레임·메뉴 → B07 공통 부품 → B08 배포
  → A01 레퍼런스 → (05·06 보강) → A02 … A34 → B09 정리
```

- B01~B03은 화면을 만들기 전에 **무엇을 변환할지**를 확정한다.
- B04~B08은 화면과 관계없는 바탕(로그인·프레임·배포)이다. OMS에서 가져온다(`07-기반이식.md`). 이것이 돌아야 화면 결과를 메뉴에서 열어 확인할 수 있다.
- **A01(레퍼런스)** 을 끝까지 변환하면서 공통 절차(05)와 체크리스트(06)를 실제에 맞게 고친다. A02부터는 "A01과 같은 방식"으로 진행한다.
- B07(공통 부품)은 A01과 함께 확정한다. A01에서 쓰는 만큼 만들고, 이후 화면에서 필요한 부품은 그 ID에서 추가한 뒤 05에 등록한다.
- B09는 모든 A가 `완료` 또는 `보류`가 된 뒤에 한다.

## A 묶음 순서

기준: **다른 화면이 쓰는 데이터를 관리하는 화면을 먼저** 한다. 결과를 바로 확인할 수 있기 때문이다(예: 권한·메뉴 화면을 고치면 B06 메뉴 API 결과가 바뀐다).

| 순서 | 묶음 | ID | 이유 |
|---:|:---|:---|:---|
| 1 | 권한 | A01~A08 | A01 레퍼런스(단일 테이블 CRUD). 권한 데이터는 메뉴 노출을 결정한다 |
| 2 | 메뉴 | A09~A12 | 트리 그리드 패턴. 메뉴 API가 읽는 데이터 |
| 3 | 코드 | A13~A14 | 공통코드. 다른 화면 콤보의 데이터 |
| 4 | 회사 | A15~A17 | A15는 서비스 30개로 가장 크다. 팝업 편집과 부가 데이터 생성 |
| 5 | 일자·계정 | A18~A24 | 조회 위주. 레퍼런스 패턴으로 빠르게 |
| 6 | 업무성 | A25~A34 | OMS에 없던 화면(파일 첨부·게시판·요청 처리 등). 새 패턴이 나오면 05에 추가 |
| — | 보류 | A35, A36 | 원본이 확인되면 해당 묶음에 넣는다 |

- B03 결과(SQL 차이, 새로 발견한 의존 관계)를 보고 이 순서를 고칠 수 있다. 고치면 이 표와 01의 ID 순서를 함께 고치고 B03 작업기록에 남긴다.

## ID 하나의 진행 (A)

| 상태 | 하는 일 | 끝났다는 기준 |
|:---|:---|:---|
| 대기 → 분석 | 색인을 읽고 `{id}-작업방법.md`를 쓴다 | 이벤트(E-id)마다 TOBE에서 할 일, 서비스 → API, SQL 이식 목록이 정해짐 |
| 분석 → 백엔드 | Mapper·Service·Controller | 컴파일·테스트 통과, `yunhee api`로 조회 응답 확인 |
| 백엔드 → 프론트 | 화면 컴포넌트, 화면 등록 | 타입체크 통과, 메뉴에서 열림 |
| 프론트 → 확인 | 06 체크리스트로 확인하고 `{id}-결과확인.md` 작성 | 모든 항목이 `통과` / `해당없음` / `미확인(사유)` |
| 확인 → 완료 | 01 상태, `{id}-작업기록`의 비용 정리 | 01에 `완료`와 날짜 |

- 상태를 바꿀 때마다 01을 고치고 `{id}-작업기록`에 한 줄을 남긴다.
- 막혀서 진행할 수 없으면 `보류`로 바꾸고 이유와 풀릴 조건을 01 비고와 작업기록에 적는다.
